## 1. 采样管线：为什么要"中断 + 信号量 + 任务 + 队列"四件套

### 1.1 最朴素的写法为什么不行

最直觉的写法是：

```c
while (1) {
    读 MPU6050();
    处理数据();
    osDelay(5ms);
}
```

致命问题三条：

1. **节拍不准**：`处理数据()` 耗时不固定，5ms 周期实际变成 `5ms + 处理时间`，逐次漂移。
2. **处理慢就采样慢**：推理一旦慢于 5ms，采样跟着慢，数据稀疏，频谱失真。
3. **没法分优先级**：采样和处理粘在一起，没法"采样必须准、推理可以慢"。

工业级方案是**彻底解耦**：

```
[硬件定时器] ──5ms──→ [中断:打节拍] ──→ [采样任务:读传感器] ──→ [队列] ──→ [推理任务:消费]
   时钟源              生产者A             生产者B               缓冲     消费者
```

### 1.2 四个核心概念

#### 硬件定时器（Hardware Timer）

芯片里独立的计数器电路。CPU 给它设"X 微秒后中断"，时间到了它就触发中断，**完全不占 CPU**。这是节拍源。

代码中：`g_sample_timer`，周期 `SAMPLE_PERIOD_US = 5000μs = 5ms`。

#### 中断（ISR, Interrupt Service Routine）

硬件突发事件让 CPU 立刻跳过去执行的一小段函数。约束：
- 别的任务全被打断、必须立刻执行
- **不能阻塞、不能慢、不能做"等待 I/O"这种事**
- 只做最少的事，活儿尽快甩给任务

代码中：`sample_timer_cb()` 只做一件事——给信号量 +1，立刻返回。

#### 信号量（Semaphore）

可以理解为"令牌池"：
- `Release` = 投一个令牌进去
- `Acquire` = 拿一个出来，没令牌就**阻塞睡眠等着**

中断每次往池子里扔令牌（"5ms 到啦"），采样任务在 `osSemaphoreAcquire` 上睡觉，一有令牌就被唤醒去干活。**信号量 = 中断和任务之间的"门铃"**。

#### 消息队列（Message Queue）

FIFO 缓冲区。生产者放数据进去，消费者拿数据出来。
- 代码中：`g_imu_queue`，深度 `IMU_QUEUE_DEPTH = 128`，每格存一个 `imu_sample_t`（6 个 float）
- 满了直接**丢弃 + 计数**（`g_drop_count++`），保证生产者不被阻塞

**消息队列 = 采样任务和推理任务之间的"传送带"**。

### 1.3 逐段拆代码

#### 中断回调（main_task.c:81）

```c
static void sample_timer_cb(uintptr_t data)
{
    (void)data;
    (void)osSemaphoreRelease(g_tick_sem);   // 扔一个令牌, 几微秒就返回
}
```

注释里两条经验：
- **不在此读 MPU6050**：`uapi_i2c_master_read` 是阻塞调用，I2C 读 14 字节要几百μs，中断里跑会拖垮整个系统。
- **不在此重载定时器**：WS63 timer 驱动在 ISR 上下文重入 `uapi_timer_start` 会走 `in_timer_irq` 分支，与共用 timer1 的软定时器并存时存在 cycle 下溢风险。

这两条都是工程师踩过坑才写下来的——**"ISR 短小"原则 + 驱动边界条件**。

#### 采样任务（main_task.c:91）

```c
static void Sample_Task_Body(void *arg)
{
    while (1) {
        if (osSemaphoreAcquire(g_tick_sem, osWaitForever) != osOK) continue;

        (void)uapi_timer_start(g_sample_timer, SAMPLE_PERIOD_US, sample_timer_cb, 0);

        imu_sample_t sample;
        MPU6050_Read_Accel_Gyro(&sample.ax, &sample.ay, &sample.az,
                                &sample.gx, &sample.gy, &sample.gz);

        if (osMessageQueuePut(g_imu_queue, &sample, 0U, 0U) != osOK) {
            g_drop_count++;
        }
    }
}
```

两个工程要点：

- **优先级 `osPriorityAboveNormal`**：比推理任务（默认 Normal）高 → 即使推理在算东西，5ms 节拍一到调度器**立刻抢占**推理。
- **先重载定时器、再读 I2C**：定时器 5ms 是从"上次中断时刻"开始算，I2C 耗多久都不影响下次节拍。这是**减小周期抖动（jitter）的标准手法**。

如果反过来：读 I2C 耗时 500μs，下次定时器要等 "500μs + 重载" 之后才开始计时，下次中断在 5500μs 后，节拍漂 10%。

#### 启动函数（main_task.c:112）

```c
g_tick_sem  = osSemaphoreNew(TICK_SEM_MAX_COUNT, 0, NULL);
g_imu_queue = osMessageQueueNew(IMU_QUEUE_DEPTH, sizeof(imu_sample_t), NULL);
if (g_tick_sem == NULL || g_imu_queue == NULL) {
    return false;
}
osThreadNew((osThreadFunc_t)Sample_Task_Body, NULL, &attr);
uapi_timer_create(SAMPLE_TIMER_INDEX, &g_sample_timer);
uapi_timer_start(g_sample_timer, SAMPLE_PERIOD_US, sample_timer_cb, 0);
```

#### 关于 `g_tick_sem = NULL` 这个易混点

```c
static osSemaphoreId_t g_tick_sem = NULL;   // ① 第 70 行
...
g_tick_sem = osSemaphoreNew(...);            // ② 第 114 行
```

很多新手会问："不是 NULL 吗，那中断怎么 release？" 答案是：

- ① 是**变量的"出生值"**——程序刚加载时是 NULL
- ② `osSemaphoreNew(...)` 实际去内核里**造**出一个信号量对象（malloc 一个控制块），返回它的**句柄（指针）**，把这个句柄**覆盖**到 `g_tick_sem` 里

从此 `g_tick_sem` 不再是 NULL，是指向真实信号量对象的指针。后续中断里 `osSemaphoreRelease(g_tick_sem)` 用的就是被覆盖后的值。

第 116 行的 NULL 检查是**判断创建是否失败**——内存不够时 `osSemaphoreNew` 会返回 NULL。

"声明时给 NULL → 用之前赋真值 → 用之前再检查"，是嵌入式里很标准的三段式防御性编程。

## 2. 三个数字：200Hz / 5ms / 3 秒 / 600 样本

这四个数字其实是**同一件事的四种说法**：

```
采样周期 5ms  ⇔  采样频率 200Hz  ⇔  窗口长度 3秒  ⇔  样本数 600
  (时域)         (频域)             (时间)          (个数)
```

换算关系：
- `1秒 ÷ 5ms = 200`  → 5ms 周期 ⇔ 200Hz
- `200Hz × 3秒 = 600`  → 3 秒窗口 ⇔ 600 样本

### 2.1 模型吃的到底是什么

`model-parameters/model_metadata.h`：

```
EI_CLASSIFIER_FREQUENCY               = 200    // 训练采样率
EI_CLASSIFIER_INTERVAL_MS             = 5      // 训练样本间隔
EI_CLASSIFIER_RAW_SAMPLE_COUNT        = 600    // 一窗 600 个采样点
EI_CLASSIFIER_RAW_SAMPLES_PER_FRAME   = 2      // 每点 2 通道
```

模型输入是 **600 × 2** 二维数组：

```
样本号:    0      1      2     ...   598    599
|acc|:   [a0]   [a1]   [a2]   ...  [a598] [a599]   ← 通道1
|gyro|:  [g0]   [g1]   [g2]   ...  [g598] [g599]   ← 通道2

时间:    0ms    5ms   10ms   ...  2990ms 2995ms     共 3 秒
```

### 2.2 为什么必须严格 200Hz / 5ms

模型训练时用的是 200Hz 数据。NN 权重对"相邻样本间的时间间隔"有**隐含假设**——它学到的是"5ms 步进下，加速度变化多快算冲击"。

| 实际采样率 | 后果 |
|----|----|
| 200Hz (5ms) ✅ | 训练分布匹配 |
| 100Hz (10ms) ❌ | 600 样本跨度变 6 秒，冲击波形被稀释 |
| 400Hz (2.5ms) ❌ | 600 样本只覆盖 1.5 秒，自由落体段被截 |
| 200Hz 但抖动大 ⚠️ | 表面对，但样本间忽快忽慢，频域失真 |

所以代码不惜搞中断+信号量+高优先级任务这套，就为了**死磕 5ms 准时**。这是模型能工作的底线。

### 2.3 推理频率 ≠ 采样频率

- **采样**：200Hz，每 5ms 一次（恒定，不能停）
- **预处理**：每来一个样本就更新一次环形缓冲（200Hz，几乎不耗时）
- **推理**：**事件驱动**，路径B 触发时才调用一次 NN（可能几小时一次，也可能不调）

为什么不能"每 5ms 推一次"？

```
run_classifier() 一次耗时 ~80ms (TFLite Micro 在 WS63 上的典型量级)
5ms 来一个样本 → 推理永远跑不完, CPU 100%, 系统崩
```

所以是：

```
采样:   ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━  连续 5ms 节拍
        │  │  │  │  │  │  │  │
预处理:  push push push push push ...     每样本更新环形缓冲
                  │
                  │ 路径B 状态机检测到候选事件
                  ▼
NN推理:        [────── 80ms ──────]      几秒/几分钟才一次
```

## 3. 为什么不能用 osDelay 替代硬件定时器

main_task.c:46 注释直接写了：

> *"osDelay 的分辨率只有 10ms 且有抖动,无法胜任。"*

### 3.1 硬证据：LiteOS 系统 tick 配置

WS63 LiteOS 的 tick 配置在多处：

```
kernel/liteos/.../tools/build/config/ws63.config:86
    LOSCFG_BASE_CORE_TICK_PER_SECOND=100         ← WS63 板配置
kernel/liteos/.../tools/build/config/ws63_iot.config:87
    LOSCFG_BASE_CORE_TICK_PER_SECOND=100
kernel/liteos/.../tools/build/config/ws63_xts.config:87
    LOSCFG_BASE_CORE_TICK_PER_SECOND=100
```

三个 WS63 配置全是 100 —— 系统 tick 频率 = 100Hz，**1 tick = 10ms**。

CMSIS-RTOS2 的 `osDelay()` 在 LiteOS 适配层里最终调用 `LOS_TaskDelay(tick 数)`，把毫秒换算成 tick。100Hz tick 下：

```
osDelay(5)  → 想等 5ms  → ceil(5/10) = 1 tick → 实际 10ms
osDelay(10) → 想等 10ms → 1 tick = 10ms ✅
osDelay(15) → 想等 15ms → ceil(15/10) = 2 tick → 实际 20ms
```

**`osDelay(5)` 直接被向上对齐到 10ms**。

### 3.2 还有抖动

注释提到"且有抖动"，物理来源：

1. **进入 osDelay 时机不对齐 tick 边界**：在 tick 过了 3ms 时调用 `osDelay(10)`，下一个 tick 还有 7ms，再加 10ms = 实际 17ms
2. **唤醒后不一定立刻被调度**：tick 到达 → 任务转 READY，但 CPU 此刻在跑别的高优先级任务
3. **tick 中断本身可能被屏蔽几微秒**：临界区里 tick 中断暂时挂起

`osDelay(5)` 在 WS63 上实际可能是 **10ms ~ 20ms 之间不固定**，对 200Hz 严格节拍完全不可接受。

### 3.3 硬件定时器 vs osDelay

```
osDelay (软件)                     uapi_timer (硬件)
─────────────────────             ─────────────────────
依赖系统 tick (100Hz)              直接挂在芯片 timer 外设
最小粒度 10ms                       最小粒度 微秒级
要等调度器                          中断直接触发,不等谁
精度 ±10ms                          精度 << 100μs
```

代码用 `SAMPLE_PERIOD_US = 5000U` 调 `uapi_timer_start`（微秒为单位），就是要绕开 OS tick 的粗粒度，直接走硬件计数器。

### 3.4 工程习惯

任何一个"系统 X 的分辨率是 Y"的断言，都应该能追到一个 `#define` 或一份芯片手册。否则就是"听说"——可能对，但说不清。

## 4. 两个缓冲区：队列 vs 环形缓冲

这是工程里**最容易混淆**的一点。

| 缓冲区 | 在哪 | 容量 | 角色 |
|--------|------|------|------|
| **队列** `g_imu_queue` | main_task.c | **128** 个样本 | 跨任务的"传送带" |
| **环形缓冲** `g_ring[]` | ei_fall.cpp:41 | **600** 个样本 | 模型 3 秒窗口的"水库" |

模型**不是从队列读 600 个**——队列从来没装过 600 个。

### 4.1 完整数据流

```
┌───────────────────────────────────────────────────────────────────┐
│  采样任务 (200Hz, 高优先级)                                        │
│  每 5ms 读 MPU6050 → 塞入队列                                      │
└──────────────────────┬────────────────────────────────────────────┘
                       │ 每 5ms 入 1 个
                       ▼
                ┌───────────────┐
                │ g_imu_queue   │  ← 队列 (128 格)
                │ [ ][ ][ ][ ]..│     只是任务间的"传送带"
                └──────┬────────┘     正常情况几乎是空的!
                       │ 每 5ms 取 1 个 (osMessageQueueGet)
                       ▼
┌───────────────────────────────────────────────────────────────────┐
│  推理任务 Fall_Detect_Task_Body                                    │
│  while (1) {                                                       │
│    osMessageQueueGet(g_imu_queue, &sample, ...);    ← 取一个      │
│    EI_Fall_Push(sample);            ──────────┐                   │
│    Fall_Algo_Process(sample);                 │                   │
│    if (路径B 触发) EI_Fall_Classify();        │                   │
│  }                                            │                   │
└───────────────────────────────────────────────┼───────────────────┘
                                                │ 每 5ms 推 1 个
                                                ▼
                                       ┌────────────────────┐
                                       │ g_ring[1200]       │  ← 环形缓冲
                                       │ (600 样本 × 2 通道)│    模型的真正"内存"
                                       │ 满了循环覆盖最旧的 │    永远存最近 3 秒
                                       └────────┬───────────┘
                                                │ 路径B 触发时
                                                ▼ 一次性展开
                                       ┌────────────────────┐
                                       │ g_window[1200]     │  ← 推理输入
                                       │ (按时间顺序排好)   │
                                       └────────┬───────────┘
                                                ▼
                                         run_classifier()
                                         → fall%, normal%
```

### 4.2 队列大部分时间是空的

main_task.c:213：

```c
osMessageQueueGet(g_imu_queue, &sample, NULL, osWaitForever);
EI_Fall_Push(sample);                       // 立刻消费
Fall_Algo_Process(sample);                  // 立刻消费
```

**取一个、立刻消费、循环回去取下一个**。两次取之间只隔几十μs（`EI_Fall_Push` 和 `Fall_Algo_Process` 都是几个加减乘除）。生产端每 5ms 才入一个。所以队列**正常运行时基本一直是 0~1 个样本**。

队列水位升高只在 NN 推理那 80ms 内：

```
路径B 触发那一刻:
  推理任务陷入 run_classifier() (~80ms 不返回)
       ↓
  采样任务继续以 200Hz 入队 (80ms 内 16 个样本)
       ↓
  队列水位短暂升到 16
       ↓
  run_classifier 结束, 推理任务回来快速消费, 队列回到 0
```

**128 这个深度的设计意图**：

```
最坏情况 = run_classifier 时长 × 200Hz
         = 80ms × 200 / 1000
         = 16 个样本

设 128 = 给推理时长留 8 倍余量 (640ms 都不丢数)
```

128 不是为"装够一次推理的数据"设计的，是为"挺过一次推理过程的入队压力"设计的。

### 4.3 600 个样本在环形缓冲里

`ei_fall.cpp:41-43`：

```c
static float    g_ring[EI_FALL_FRAME] __attribute__((aligned(16)));  // 1200 floats = 600 × 2
static uint32_t g_ring_head  = 0;     // 写指针
static uint32_t g_ring_count = 0;     // 已写入数(封顶 600)
```

每次推理任务从队列拿一个样本，调用 `EI_Fall_Push()` (ei_fall.cpp:66)：

```c
g_ring[g_ring_head*2 + 0] = |acc|;       // 写当前槽位
g_ring[g_ring_head*2 + 1] = |gyro|;
g_ring_head = (g_ring_head + 1) % 600;   // 循环递增
if (g_ring_count < 600) g_ring_count++;  // 计数器封顶
```

环形缓冲**永久滚动**：
- 上电后前 3 秒：缓冲填充（`g_ring_count` 从 0 涨到 600）
- 之后：永远存"**最近 3 秒**"——每写一个新样本，最老的那个被覆盖

### 4.4 为什么不能让队列直接装 600

| 维度 | 队列 600（一次取） | 环形 600（持续累积，当前实现） |
|------|-------------------|---------------------|
| 内存 | 600 × 6 floats = 14.4KB（6 轴原始） | 600 × 2 floats = 4.8KB（已压缩为幅值） |
| 触发时延 | 必须等队列积满 600（=3 秒）才能推理 | 缓冲一直就绪，触发瞬间立刻可推 |
| 推理频率 | 每 3 秒最多一次 | 任意时刻都能触发（事件驱动） |
| 数据覆盖 | 推理时数据是 3 秒前刚开始的 | 永远是"截至现在的最近 3 秒" |

核心差异：**环形缓冲让推理"随时可发"**——路径B 在任意一帧判定为候选跌倒，立刻就能拿到包含那个冲击事件的 3 秒上下文。这是事件驱动检测必须的。

### 4.5 嵌入式管线的两层缓冲模式

这是个**通用模式**：

```
硬件 → [跨任务通信缓冲(小)] → [应用语义缓冲(大)] → 算法/模型
       (queue / DMA buffer)    (ring / sliding window)
```

队列管"别丢数"，环形缓冲管"保留历史"。**两个职责，两个缓冲**。无论是摄像头→CV、麦克风→ASR、IMU→手势/跌倒，骨架都一样。

### 4.6 数据形态对照

| 阶段 | 在哪 | 容器 | 容量 | 数据形态 |
|------|------|------|------|---------|
| ① 硬件读 | mpu6050.c | 局部变量 | 1 个样本 | 6 轴原始 (g, dps) |
| ② 跨任务 | main_task.c | 队列 g_imu_queue | 128 | 6 轴原始 (imu_sample_t) |
| ③ 累积窗口 | ei_fall.cpp | 环形 g_ring[] | 600 | 2 通道幅值 (milli-g, centi-dps) |
| ④ 喂模型 | ei_fall.cpp | 展平 g_window[] | 600 | 2 通道幅值（按时间顺序） |

模型读的是 ④，但 ④ 数据来自 ③，③ 由推理任务**一个一个**从 ② 搬过来。

## 5. 特征预处理：朝向无关的 2 通道幅值

`EI_Fall_Push()` (ei_fall.cpp:66) 把 6 轴原始数据压缩成 2 通道幅值：

```c
float acc_mag = sqrtf(ax*ax + ay*ay + az*az) * 1000.0f;   // → milli-g
float gyr_mag = sqrtf(gx*gx + gy*gy + gz*gz) * 100.0f;    // → centi-dps
```

### 5.1 为什么用幅值不用 6 轴原始值

模块佩戴朝向不固定 —— Z 轴未必朝上。如果模型直接吃 6 轴，训练时不同朝向的样本会让模型学不到稳定模式。**幅值（向量长度）只看大小不看方向**，朝向旋转不改变幅值，模型对佩戴方向不敏感。

这跟路径B 算法里"用 `|acc|` 而不是 `ax/ay/az` 单轴"是同一个思想。

### 5.2 量纲为什么要 ×1000 / ×100

模型训练时是 `make_features.py` 生成的 CSV，单位是 milli-g / centi-dps（整数化便于训练）。**部署时必须维持完全一致的量纲**，否则模型见到的数值范围跟训练完全错位。

代码注释明确警告（main_task.c:185）：

> *"关键: 将来训练好的模型, 推理时必须喂入同样比例的数值(ax*1000, gx*100),
>  否则会重蹈 SisFall 那次'训练/部署量纲不一致'的覆辙。"*

**训练/部署的"两个一致性"**：
1. **量纲一致**（单位匹配）
2. **时间轴一致**（采样率与窗口长度匹配）

两条同时满足，模型才能"按训练时的样子"工作。

## 6. 算法层：路径B 确定性状态机（真正在做检测的）

### 6.1 设计哲学：物理事件链 vs 模式识别

ML 模型把跌倒看成"3 秒加速度/角速度窗口的分类问题"，但：
- 蹲下、坐下、躺下、跳跃落地，在频域/统计特征上**和跌倒高度相似**
- 训练样本中的跌倒姿态有限，泛化差
- 黑盒，调不动，调一次要重训

反向思路：**真实跌倒在时间轴上必然出现一组固定物理事件**：

```
失重 (人在空中) → 硬冲击 (撞地) → 静止 (躺地不动) → 躯干由直变倒
   必要           必要              必要              必要
```

四个都满足才报。这是用"事件因果链"代替"模式识别"——后者天然有可解释性，每个否决都能在串口日志里看到原因。

### 6.2 四态状态机

```
ST_IDLE  ──失重起──→ ST_FREEFALL  ──失重结束且立刻冲击──→ ST_POST_IMPACT
                          │
                          └──失重结束但没冲击──→ ST_IMPACT_WAIT ──冲击到来──→ ST_POST_IMPACT
                                                       │
                                                       └──1秒内没冲击──→ RESET
```

**为什么要拆出 `ST_IMPACT_WAIT`**：物理上人从开始失重到落地有间隙（失重 70~750ms，落地姿态调整还有 100~1000ms）。如果只用三态 `IDLE → FREEFALL → POST_IMPACT`，会出现漏报：失重期一结束就要求紧接冲击 → 真摔中间 100ms 的"贴近 1G"过渡会被当成"失重结束但没事"复位。

所以 `ST_IMPACT_WAIT` 是给"失重已结束、冲击还没到"留的宽容期（~1 秒）。

### 6.3 四重否决，每条对应一个真实攻击场景

报警最后判定在 `fall_algo.c:208-232`：

| # | 判据 | 阈值 | 否决谁 |
|---|------|------|--------|
| 1 | 冲击后是否静止 | 静止样本 ≥ 50% | 剧烈摇晃手机、骑车颠簸 |
| 2 | 硬冲击 | impact_max ≥ 4.0G | 快速蹲下、用力坐下（实测 ≤3.1G） |
| 3 | 倾角 | tilt ≥ 45° | 原地起跳落地（躯干仍直） |
| 隐含 | 必须有失重段 | FF 持续 ≥70ms | 静态轻放、慢动作 |

代码注释里的**实测值**（fall_algo.c:41-46）：
- 真跌倒 impact ≥ 5.3G，蹲坐 ≤3.1G → 中点 4.0G
- 真跌倒 tilt ≥ 73°，留余量取 45°

"实测两类样本的分布、取中间值留余量" —— 这是确定性算法该有的调参纪律。

### 6.4 最巧的一笔：朝向无关的倾角判据

`fall_algo.c:93-110` 是整个算法最值得品的部分。

**问题**：腰部模块怎么戴方向是随机的，怎么知道人"由直立变倒下"？

**解法**：不看绝对方向，**只看变化量**：
- IDLE 静止时，传感器读到的重力向量就是"直立时的下方"，定义为基准 `g_ref`
- 摔倒静止后再测一次重力向量 `g_post`
- 两个向量的夹角就是躯干倾倒的角度

```
真跌倒：站立时重力沿身体长轴 → 躺下时重力垂直于长轴 → 夹角 ≈ 90°
原地跳：站立和落地后躯干都直立 → 夹角 ≈ 0°
```

实现里几个工程心思：

```c
// fall_algo.c:122-134
if (acc >= 0.85 && acc <= 1.15) {     // 只在真静止时才更新
    s_gref_x += GREF_ALPHA * (ax - s_gref_x);
    ...
}
```

- 只在 IDLE 且 |acc|≈1G 时更新 → 避免走路时瞬时加速度污染参考
- α=0.02 → 时间常数 ≈ 50 个样本 ≈ 0.25 秒，对慢漂移敏感、对短暂动作不敏感
- `fall_algo_reset()` 故意**不重置 `s_gref_*`**（fall_algo.c:89） → 复位状态机时保留长期姿态参考

```c
// fall_algo.c:95-96
if (!s_gref_valid || s_gpost_n == 0) return 180;
```

**"保守不漏报"原则**：基准缺失时假设已倾倒，让倾角判据失效而不是误否决。生命安全场景里这是对的——宁可多报误报（用户能解除），不可漏报真摔（用户摔了没人知道）。

### 6.5 参数表速查

| 宏 | 值 | 物理含义 | 调参方向 |
|---|---|---|---|
| `FF_ACC_G` | 0.75G | 失重判定线 | 太高→走路也算失重；太低→真摔的"半失重"被漏 |
| `FF_MIN_SAMPLES` | 14 (70ms) | 失重最短时长 | 排除抖动、急停 |
| `FF_MAX_SAMPLES` | 150 (750ms) | 失重最长时长 | 超过=异常（电梯下降？传感器掉地？） |
| `IMPACT_ACC_G` | 2.20G | 冲击触发线（粗筛） | 先把候选事件捞进来再用 4.0G 细筛 |
| `IMPACT_WINDOW` | 200 (1s) | 失重后多久内必须冲击 | 1G 自由落体 1s 约 5m，物理上够用 |
| `IMPACT_SETTLE` | 100 (0.5s) | 冲击后翻滚期 | 跳过不算静止 |
| `STILL_WINDOW` | 200 (1s) | 跳过沉降后再观察的窗口 | 真摔通常 0.5s 后已基本不动 |
| `STILL_LOW/HIGH_G` | 0.6 / 1.4G | "静止样本"的 \|acc\| 区间 | 围绕 1G ±0.4，留呼吸/手颤的余量 |
| `STILL_MIN_PCT` | 50% | 窗口内静止占比阈值 | 真摔通常 >80%，50% 留余量 |
| `IMPACT_HARD_G` | **4.0G** | **硬冲击主判据** | 实测蹲坐 ≤3.1G、真摔 ≥5.3G 的中点 |
| `TILT_DEG_MIN` | **45°** | **躯干倾角主判据** | 实测真摔 ≥73°，对半留余量 |

`IMPACT_ACC_G=2.2G` 和 `IMPACT_HARD_G=4.0G` 是**两道闸**——前者负责进入状态、后者负责最终判决。两阶段的好处：避免坐下这类柔冲击在初筛阶段被丢掉（丢掉就没机会进入 POST_IMPACT 观察静止/倾角），但又不会被它误报。

### 6.6 几个容易忽略的边界处理

1. **fall_algo.c:151** 失重 <70ms 直接 reset → 阻挡抖动
2. **fall_algo.c:153** 失重期内已冲击 → 直接跳 POST_IMPACT，不经过 IMPACT_WAIT
3. **fall_algo.c:186** IMPACT_WAIT 超时无冲击 → reset（"失重但没摔"，比如轻放）
4. **每次确认/否决后立刻 reset** → 释放状态机
5. **3 秒冷却在 main_task.c 不在算法里** → 算法只判定，"防抖"留给上层

"算法只回答 yes/no、不管时间防抖"的分层很干净，让算法本身可以被任意场景复用。

### 6.7 可观测性：调参实验台

代码里每次事件无论判定结果都打印四个调参变量：

```c
printf("[Fall] CONFIRMED (impact %.2fG, tilt %d°, ffmin %.2fG, still %u%%)");
printf("[Fall] rejected: soft impact, sit/squat? (impact %.2fG, ...)");
printf("[Fall] rejected: upright, jump? (tilt %d°, ...)");
```

把算法当成**带可观测性的调参实验台**：现场穿戴、做各种动作、用串口日志看 4 个变量的分布，根据分布间距调阈值。**这是没有 ML 数据集时的手工"决策树训练"**。

## 7. NN 推理：路径A 复核（仅在路径B 触发后调用）

### 7.1 调用时机

只有 `Fall_Algo_Process()` 返回 1，且不在冷却期时，才调用 `EI_Fall_Classify()`：

```c
// main_task.c:245-272
} else if (status == 1) {
    ei_fall_result_t nn = EI_Fall_Classify();
    if (nn.valid && nn.normal_percent >= NN_VETO_NORMAL_PCT) {
        // NN 强烈不同意 → 否决
    } else {
        // 触发告警
    }
}
```

### 7.2 推理流水

`EI_Fall_Classify()` (ei_fall.cpp:85)：

1. 检查环形缓冲是否满 600 (`g_ring_count >= 600`)，不满直接返回 valid=false
2. **环形展开为线性窗口**：从 `g_ring_head` 开始（最旧样本）分两段 memcpy 到 `g_window`
3. `numpy::signal_from_buffer(g_window, 1200, &signal)` 包装为 EI 的 `signal_t`
4. **`run_classifier(g_handle, &signal, &result, false)`** —— TFLite Micro 推理
5. 遍历 `result.classification[]`，按 label 名提取 fall_prob / normal_prob
6. 返回 `{valid, fall_percent, normal_percent}`

### 7.3 NN 角色：否决者而非判决者

main_task.c:33-37 注释：

> *"NN 复核否决阈值: 路径 B 触发后, 仅当 NN 以 >= 此置信度判为 "normal" 才否决报警。
>  ...真摔 normal% 远低于 95, 故设 95: 既不会误否决真摔, 又能在路径 B 误触发且 NN 高置信判 normal 时挡掉误报。"*

`NN_VETO_NORMAL_PCT=95` 设得很高，意味着只有 NN **极度自信**才能压住路径B 的报警。这是给 NN "不可信" 留的保护壳。

### 7.4 路径B vs 路径A 对比

| 项 | 路径B (fall_algo) | 路径A (EI NN) |
|---|---|---|
| 输入 | 即时单样本 (5ms 一次) | 600 样本窗口 (3s) |
| 时延 | 0 ms | 至少 3s 才有一次结论 |
| 可解释 | 4 个数值 + 状态名 | softmax 黑盒 |
| 调参 | 改 #define 重编译 | 重新采集训练数据 + 重训 |
| 对未见动作 | 有明确否决规则 | 行为未知 |

NN 想做的事（"这 3 秒像不像跌倒"）在物理事件链面前是个**冗余而模糊**的判定。所以最终 NN 在这套系统里被降级为**保险丝**，不参与正向判决。

## 8. 关键认知小结

把今天的分析压缩成 5 句话：

1. **队列管"别丢数"，环形缓冲管"保留历史"**。两个职责完全不同，正常情况队列几乎是空的，600 样本永远住在环形缓冲里。
2. **NN 是"否决者"不是"判决者"**。路径B 状态机才是真正在做检测的，NN 只在路径B 触发后被叫来复核，且要 ≥95% 才能否决。
3. **5ms 节拍准时是模型工作的底线**。所以代码不惜搞中断+信号量+高优先级任务，绕开 `osDelay` 的 10ms 分辨率。
4. **训练/部署的两个一致性**：量纲一致（×1000 / ×100）+ 时间轴一致（200Hz/600样本/3秒）。任一不满足模型就废。
5. **可观测性是确定性算法的命脉**。fall_algo 每次事件都打印 4 个变量，把算法当成一个可调参的实验台——这是没有 ML 数据集时的"手工训练"。

---

## 9. 设计可优化的方向

如果未来要真正让 NN 起作用，不是去替换路径B，而是：

- **把 NN 输出作为路径B 某个阈值的软调制**：NN 越倾向 normal，`IMPACT_HARD_G` 阈值越往上抬
- **用 NN 做事件类型细分**：区分前摔/后摔/侧摔，路径B 只回答"有没有摔"

这样 NN 和确定性算法能形成真正的互补，而不是互相牵制。
