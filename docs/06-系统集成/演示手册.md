## 1. T-30 分钟:预飞行自检清单

依次过一遍,每条 1 分钟以内做完。任一条不过就**就地解决**,不要往下走。

### A. 物料
- [ ] 板 A(手环)、板 B(网关)各一块,Type-C 线 ×3,V100C 4G 模块 ×1
- [ ] WS2812B 灯带、蜂鸣器、4G 天线、SIM 卡(已开机激活、有话费)
- [ ] 笔记本一台,后端能跑 `python3`,装好 `tencentcloud-sdk-python`(可选)
- [ ] 备用充电宝(板 B 演示时可脱开电脑)、备用 2.4G 路由器/手机热点

### B. 网络
- [ ] 演示场地的 2.4G WiFi 能用,**不是 5G**
- [ ] 配置 `fall_alert_gateway_config.h` 的 SSID/密码已经按今天现场改过
- [ ] 后端 PC `ipconfig` 看到的 IPv4 已经填进 `FALL_GATEWAY_SERVER_HOST`,**已重编 + 烧录**
- [ ] PC 防火墙允许 Python 入站(8080 端口)

### C. 板端
- [ ] 板 A 上电后,串口看到 `[MPU6050] init ok` 和 `[Monitor] state=NORMAL`
- [ ] 板 B 上电后,串口看到:
  - `[FALL_GW] Wi-Fi connected.`
  - `[FALL_GW] DHCP success, ip=...`
  - 灯带变绿常亮(待机)
- [ ] 4G:板 B 串口看到 `[DTU] tx ready`,V100C 自身 LED 表明已注网(具体看模块说明)

### D. 后端
- [ ] `tools/fall_alert_backend.env` 真实文件已存在(不是 `.example`)
- [ ] `FALL_NOTIFY_PROVIDER=pushplus`、`FALL_NOTIFY_DRY_RUN=0` 已置位
- [ ] `PUSHPLUS_TOKEN` 已填、`FALL_BACKEND_TOKEN` 跟板端一致
- [ ] `python fall_alert_backend_demo.py --port 8080` 已起来,控制台显示监听 0.0.0.0:8080
- [ ] PushPlus 微信号已收到一条手动 curl 的测试推送(见下)

### E. 手动注入一次链路验证

在 T-30 阶段必须**手动 curl 一次**,确认全链路打通:

```powershell
curl.exe -X POST http://127.0.0.1:8080/api/fall-alert ^
  -H "Authorization: Bearer 你的_FALL_BACKEND_TOKEN" ^
  -H "Content-Type: application/json" ^
  -d "{\"device_id\":\"demo-precheck\",\"event\":\"fall\",\"payload\":1,\"event_count\":1}"
```

- 后端控制台:`[NOTIFY] pushplus ok`
- 微信:几秒内收到一条"Fall detected"测试推送
- 收到 → 链路 OK,删除 PushPlus 历史记录,准备正式演示
- 没收到 → 立刻按 §4 回退预案处理

### F. cooldown 清零

`FALL_GATEWAY_CLOUD_COOLDOWN_MS = 60000` 意味着 1 分钟内只发一次告警。预检完之后**等满 60 秒再开始演**,或者把这个宏临时改成 5000 重编。

## 3. 演讲者脚本(7 分钟版)

> 加粗的是**讲什么**,后面是**做什么**(动作)。可以根据评委兴趣删减。

### Step 1(30s)— 开场架构图
> **"这是一套星闪 + TinyML 的端侧跌倒检测系统,核心是把推理放到手环本地、把报警走星闪 + WiFi + 4G 三条独立链路。"**

→ 指向屏幕上的架构图(`assets/figures/*` 里的图,或者 ROADMAP.md 顶部)

### Step 2(60s)— 实物巡场
> **"左边这块是手环板,装了 MPU6050 三轴加速度计 + 陀螺仪,跑 LiteOS + Edge Impulse TinyML 模型。右边是网关板,负责本地声光告警 + WiFi 上云 + 通过 4G DTU 拨打监护人电话。"**

→ 指两块板;指灯带(绿) → 待机;指笔记本 → 后端服务在跑

### Step 3(60s)— 数据 + 模型简述
> **"训练数据用了 SisFall 公开数据集加自采的腰部跌倒数据,在 Edge Impulse 上训练了一个轻量卷积网络。最终判定是确定性算法主路径 + 神经网络复核否决的混合策略,既保召回又压假阳。"**

→ 翻到 PC 上的 `docs/04-TinyML模型/EdgeImpulse_WS63_部署调试记录_2026-05-07.md` 或推理日志

### Step 4(90s)— 模拟跌倒(核心演示)
> **"我现在模拟一次跌倒。"**

→ **快速向下抛手环到桌面**(配合手势,确保 ≥ 2g 冲击,但不要真摔坏)

应该立刻看到:
1. 板 A 串口:`[FALL] DETECTED, send 0x05`
2. 板 B 串口:`[CLIENT] 2` → 灯带变红闪、蜂鸣器响起、LED 亮
3. 1~3 秒内:`[FALL_GW] fall alert uploaded.` + 后端控制台 `[NOTIFY] pushplus ok`
4. 5 秒内:**笔记本屏幕上的 PushPlus 微信通知弹出**(评委可看)
5. 10~30 秒内:**监护人手机收到短信 + 来电**(可让评委拿你的备用手机当"监护人手机")

> **"刚才的链路是:手环判定 → SLE 0.x 毫秒级传给网关 → 网关同时走 WiFi 推送给监护人微信,以及走 4G 给监护人拨电话发短信。即使现场 WiFi 挂了,4G 这条独立链路还能保住报警。"**

### Step 5(40s)— 关停告警
> **"告警会保持 10 秒自动停。"**

→ 等 10 秒,灯带回到绿色待机,蜂鸣器停。**不要手动复位**,让评委看到"自动恢复"。

### Step 6(60s)— 户外化方向
> **"WiFi 这条链路适合室内/比赛环境;户外产品化我们会把 WiFi 替换成 4G Cat.1 + GPS/北斗,做成完全脱离电脑的独立报警器。这部分方案在 `远程报警链路与户外化方案-2026-05-10.md` 里有详细分析。"**

→ 翻一下那份文档的章节标题让评委扫一眼

### Step 7(40s)— 收尾要点
> **"几个亮点想留给评委:一是 SLE 端到端时延实测在 X 毫秒级别,比 BLE 快;二是混合判定把假阳率压到 Y;三是整个系统已经做了灯带、蜂鸣器、微信、短信、电话五种告警通道。谢谢。"**

→ X / Y 用 `docs/06-系统集成/实时性_可靠性_星闪优势量化分析.md` 和 `性能测试与SLE延迟验证方法.md` 里的数据

## 4. 现场出问题的回退预案

> 顺序按"切换成本从低到高"。先按 1 试,不行再 2,以此类推。

### 4.1 推送收不到(微信端没弹)

| 多半原因 | 应急动作 |
| --- | --- |
| PushPlus 服务抖动 | 不要重试,**口播**"微信刚刚那条来得稍慢,我们这里串口和后端日志已经显示发送成功"——指给评委看日志 |
| `FALL_NOTIFY_DRY_RUN=1` 没改 | 后端 Ctrl+C 停,改 `.env`,重启,**跳过这次演示重新触发** |
| Token 漏填 | 同上,但先把替补 Token 备好 |

### 4.2 后端连不上 / WiFi 链路挂

- **不要重连 WiFi 试图救场**,会让你卡 1~2 分钟,评委的耐心一秒一秒掉
- 直接口播切到 4G 故事线:"WiFi 这条链路演示设备临时和场地热点失联,但 4G 是独立链路,**我们看监护人手机**" → 让评委盯手机
- 演示完后再排错

### 4.3 4G 也挂了

- 只剩本地声光告警,**这是设计上的最后一道防线,正好讲故事**:
  > "这套系统设计了三层降级:WiFi → 4G → 本地声光。即使所有网络都失效,只要佩戴者动了一下,设备本地就报警,旁边的人就能听到看到。"
- 把灯带闪 + 蜂鸣器响这段拉长,作为收尾

### 4.4 板子直接卡死/重启

- **不要重新烧录**,演示现场没时间
- 用备用板子(应提前烧好同一版本固件)
- 如果备用板子也没有,直接跳过演示动作,口播架构 + 给评委看预录的视频(放在 PC 桌面)

### 4.5 灯带乱亮

- 时序失真问题在 2026-05-15 已经修过,如果还乱:
  - 多半是地没共,把灯带 GND 重新插紧
  - 或者灯带 5V 不够,换一路 USB 给灯带单独供电

### 4.6 演示完忘了关后端 / 灯带还在闪

- 评委走后:Ctrl+C 关后端、拔灯带 USB 即可
- **不要在评委面前关**,会显得"演完就拆台"

## 5. 答辩 Q&A 速查

| 评委可能问 | 一句话答 |
| --- | --- |
| "和 BLE 比有什么优势" | 端到端时延更低、连接建立更快、组网灵活;具体数据看实时性量化文档 |
| "TinyML 模型多大" | ~几十 KB FlatBuffers,RAM 占用 ~10KB 级,完全跑在 WS63 片内 |
| "误报率怎么控制" | 路径 B 主判 + NN 复核否决,把假阳压在 ≤ X% |
| "电池能撑多久" | 3000mAh 锂电池约 30 小时(待机)/ 10 小时(频繁报警);见功耗分析 |
| "为什么不用云端推理" | 时延 + 隐私 + 离线可用,端侧推理是产品形态决定的 |
| "为什么用 PushPlus 不用短信" | 个人账号短信签名审核拿不到;后端是插件化的,有单位资质后无缝切短信 |
| "怎么防止误触发疯狂打电话" | `FALL_ALERT_4G_DTU_COOLDOWN_MS=60s` + 后端 `FALL_RATE_LIMIT_SECONDS=60`,双层冷却 |
