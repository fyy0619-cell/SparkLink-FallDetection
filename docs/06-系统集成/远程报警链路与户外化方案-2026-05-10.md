# 远程报警链路、户外化方案与问题记录（2026-05-10）

> 本文记录跌倒检测系统从“本地声光报警”扩展到“手机端远程报警”的完整过程，包括 Wi-Fi 网关、后端服务、PushPlus 微信推送、腾讯云短信受阻原因，以及户外佩戴产品化时的 4G Cat.1/DTU 方案选型。

## 1. 背景与目标

原始跌倒检测系统已经可以在 WS63 开发板上完成：

```text
MPU6050 六轴数据采集
    -> Edge Impulse TinyML 跌倒判断
    -> SLE 星闪发送跌倒信号
    -> Board B 本地蜂鸣器 / LED / WS2812B 报警
```

新的目标是：

```text
只要检测到跌倒，手机端就能收到报警通知。
```

进一步产品化目标是：

```text
佩戴者在户外运动时，不依赖旁边电脑、不依赖局域网、不依赖旁边手机，也能自动通知家属。
```

因此系统被拆成两个阶段：

| 阶段 | 目标 | 通信路径 |
| --- | --- | --- |
| 比赛演示版 | 快速稳定展示手机收到报警 | Board A -> SLE -> Board B -> Wi-Fi -> 后端 -> PushPlus 微信 |
| 户外产品版 | 人在户外也能独立报警 | 可穿戴设备 -> 4G Cat.1/DTU -> 云端 -> 手机通知 |

## 2. 当前工程中的跌倒信号位置

结合工程代码，跌倒信号来自以下链路：

| 功能 | 文件/位置 | 说明 |
| --- | --- | --- |
| AI 跌倒判断 | `application/samples/my_demo/fall_detect/src/ai_model.cpp` | `fall_risk` 概率、运动门限、连续窗口确认 |
| 主循环读取 IMU | `application/samples/my_demo/fall_detect/src/main_task.c` | 调用 `AI_Feed_And_Predict_6Axis()` |
| 跌倒报警字节 | `main_task.c` 中 `FALL_ALERT_PAYLOAD` | 当前为 `0x05` |
| SLE Server 发送 | `sle_server_task.c` | `sle_send_fall_alert()` -> `ssaps_notify_indicate()` |
| SLE Client 接收 | `sle_client_task.c` | 收到 `data[0] == 0x05` 后触发本地报警 |
| SLE ACK | `sle_client_task.c` | Client 回写 `0x06` 给 Server |

关键结论：**最合适的远程报警接入点是 Board B 的 SLE Client 收到 `0x05` 后。**

原因：

- Board A 已承担传感器采样、AI 推理和 SLE Server，不宜继续叠加复杂联网逻辑。
- Board B 是接收网关，适合扩展 Wi-Fi/4G 上报能力。
- SLE 回调中不能做阻塞网络请求，因此只投递事件，由独立任务上报。

## 3. Wi-Fi 网关实现方案

### 3.1 设计结构

比赛演示版采用：

```text
Board A：跌倒检测节点
    MPU6050 + AI + SLE Server
        ↓ SLE 0x05
Board B：报警网关
    SLE Client + 蜂鸣器/灯带 + Wi-Fi HTTP
        ↓ POST /api/fall-alert
电脑/服务器后端
        ↓ PushPlus / 后续短信语音
手机端
```

### 3.2 新增/修改文件

在 WS63 工程中新增：

```text
application/samples/my_demo/fall_detect/inc/fall_alert_gateway.h
application/samples/my_demo/fall_detect/inc/fall_alert_gateway_config.h
application/samples/my_demo/fall_detect/src/fall_alert_gateway.c
```

并在：

```text
application/samples/my_demo/fall_detect/src/sle_client_task.c
```

接入：

```c
fall_alert_gateway_init();
fall_alert_gateway_post_fall(data->data[0]);
```

设计原则：

```text
SLE notification 回调只投递事件，不直接联网；
Wi-Fi 连接、HTTP 发送、失败重试都放到 fall_alert_gateway_task 后台任务中。
```

### 3.3 板端配置

配置文件：

```text
application/samples/my_demo/fall_detect/inc/fall_alert_gateway_config.h
```

示例：

```c
#define FALL_GATEWAY_WIFI_ENABLED       1
#define FALL_GATEWAY_WIFI_SSID          "YOUR_2G_WIFI"
#define FALL_GATEWAY_WIFI_PASSWORD      "YOUR_WIFI_PASSWORD"

#define FALL_GATEWAY_SERVER_HOST        "192.168.1.100"
#define FALL_GATEWAY_SERVER_PORT        8080
#define FALL_GATEWAY_SERVER_PATH        "/api/fall-alert"
#define FALL_GATEWAY_DEVICE_ID          "ws63-fall-client-001"
#define FALL_GATEWAY_AUTH_TOKEN         "change-me-demo-token"
#define FALL_GATEWAY_CLOUD_COOLDOWN_MS  60000U
```

注意：

- `FALL_GATEWAY_SERVER_HOST` 必须填电脑/服务器在同一网络下的 IPv4 地址。
- 不能填 `127.0.0.1`，因为那是板子自身。
- 如果使用手机热点，电脑和 Board B 必须连接同一个热点。
- WS63 更适合使用 2.4 GHz Wi-Fi；校园网/5 GHz/隔离网络容易失败。

## 5. 手机端通知：PushPlus 方案

### 5.1 为什么使用 PushPlus

原计划使用腾讯云短信/语音电话，但实际遇到资质限制：个人账号无法快速申请国内短信签名。

因此比赛演示版改用：

```text
后端 -> PushPlus -> 微信通知
```

优点：

- 个人可用。
- 开通快。
- 不需要短信签名和单位资质。
- 手机端可以实时收到通知。
- 不改变板端代码。

### 6.2 实际遇到的问题

腾讯云国内短信签名需要资质。

控制台提示：

```text
由于当前运营商不支持对个人用户进行签名报备，
自 2025年9月18日起，控制台将不再支持创建和修改个人自用资质。
个人认证用户如需申请签名，可创建他用资质。
```

当前没有学校/企业/单位资质，因此无法快速创建国内短信签名。

### 6.3 解决方案

短期比赛方案：

```text
使用 PushPlus 微信推送作为手机端报警通道。
```

长期产品方案：

```text
使用学校/企业/机构资质申请短信签名，或使用运营商 SIM 卡直接短信/电话，或接入 4G 模块独立上云。
```

答辩解释：

> 由于国内短信签名需要单位资质，比赛演示阶段采用 PushPlus 微信推送完成手机端实时报警。后端采用插件化通知架构，已预留腾讯云短信和语音接口；后续具备学校或企业资质后可无缝切换为短信和电话报警。

## 7. 遇到的问题与解决方案汇总

| 问题 | 现象 | 原因 | 解决方案 |
| --- | --- | --- | --- |
| Wi-Fi 网关没有工作 | 日志提示 `Wi-Fi gateway disabled` | `FALL_GATEWAY_WIFI_ENABLED=0` | 改为 `1` 后重新编译烧录 |
| disabled 日志刷屏 | 每隔几秒重复打印 | 后台任务循环重试 | 改为只打印一次 |
| Board B 连不上 Wi-Fi | assoc fail / DHCP fail | 热点不稳定、密码错误、5 GHz、校园网隔离 | 使用手机 2.4 GHz 热点或小路由器 |
| 后端收不到报警 | Board B 上传失败 | `SERVER_HOST` 填了旧网段 IP 或防火墙拦截 | 确认电脑与 Board B 同一热点，填电脑热点 IPv4，允许 8080 端口 |
| 不能填 `127.0.0.1` | Board B 访问失败 | `127.0.0.1` 是板子自己 | 填电脑局域网 IP |
| 腾讯云短信开通受阻 | 签名无法申请 | 个人账号无单位资质 | 改用 PushPlus；保留腾讯云接口 |
| 真实户外不可靠 | 电脑/手机热点不能常伴随 | Wi-Fi 方案只是演示原型 | 产品化改为 4G Cat.1/DTU + GNSS |
| SLE 回调不宜联网 | 可能阻塞协议栈 | 网络请求耗时不可控 | 回调只投递事件，后台任务负责上报 |
| 重复报警 | 一次跌倒可能多次触发 | AI 窗口和通信重试 | Board A 冷却 + 后端限流 |

## 8. 户外佩戴产品化方案

### 8.1 为什么当前 Wi-Fi 方案不够

当前比赛演示版依赖：

```text
Board B 附近有 Wi-Fi/手机热点
电脑或服务器正在运行后端
```

但真实产品中，佩戴者可能在户外运动。因此设备必须具备：

```text
广域联网能力
独立供电能力
定位能力
断网重试能力
误报撤销能力
```

### 8.2 推荐产品架构

```text
可穿戴跌倒检测设备
    ├── WS63 / 主控
    ├── MPU6050 / 六轴 IMU
    ├── TinyML 跌倒判断
    ├── 4G Cat.1 / DTU 模块
    ├── GPS + 北斗定位
    ├── 蜂鸣器 / 震动马达 / LED
    ├── SOS 按键 / 误报取消按键
    └── 锂电池 + 充电管理 + 大电流电源
```

通信链路：

```text
检测到跌倒
    -> 本地蜂鸣器倒计时
    -> 用户未取消
    -> 4G Cat.1 上报云端
    -> 后端 PushPlus / APP / 短信 / 电话
    -> 家属手机收到通知和位置
```

### 8.3 4G 模块选型：DTU 固件 vs AT 固件

| 对比项 | DTU 固件 | AT 固件 |
| --- | --- | --- |
| 联网参数 | 工具/网页配置 | MCU 逐条 AT 指令配置 |
| 联网维护 | 模块自动维护 | MCU 手动维护 |
| TCP/MQTT/HTTP | 多数支持透传 | 需要按协议手动 AT 配置 |
| 开发难度 | 低 | 高 |
| 适合场景 | 比赛、快速原型、稳定透传 | 深度定制、完全控制模块 |

结论：

```text
比赛/快速户外验证：优先 DTU 固件。
后续深度开发：再考虑 AT 固件。
```

### 8.4 推荐购买

推荐购买：

```text
M100MG(DTU固件) 贴片卡-带GPS+北斗 测试套装
供电电压：5-12V
```

理由：

- DTU 固件，适合串口透传快速上云。
- 带 GPS + 北斗，适合户外跌倒定位。
- 测试套装更适合调试，通常包含底板/天线/线材。
- 5-12V 供电更容易调试，4G 模块瞬时电流更稳定。

不推荐：

- 纯 AT 固件版本：开发量大。
- 不带 GPS 版本：户外报警缺少位置信息。
- 裸模块：电源、SIM、天线、串口调试麻烦。

下单前建议询问卖家：

```text
这个“M100MG(DTU固件)贴片卡-带GPS+北斗测试套装，5-12V供电”是否支持串口透传到 HTTP/MQTT/TCP 服务器？是否带 4G 天线、GPS/北斗天线和测试底板？
```

### 8.5 与当前工程如何衔接

当前上层接口保持不变：

```c
void fall_alert_gateway_post_fall(uint8_t source_payload);
```

后续可以扩展多个底层实现：

```text
fall_alert_wifi.c      // 当前 Wi-Fi HTTP 上报
fall_alert_4g_dtu.c    // 未来 4G DTU 串口透传
fall_alert_4g_at.c     // 未来 AT 指令控制
fall_alert_local.c     // 本地蜂鸣器/灯带/震动
```

4G DTU 版本的逻辑：

```text
Board / MCU 收到跌倒事件
    -> UART 输出 JSON
    -> DTU 模块自动通过 4G 发送到服务器
```

示例串口数据：

```json
{"device_id":"ws63-wearable-001","event":"fall","payload":5,"lat":30.000000,"lng":120.000000}
```

## 11. V100C / Air780EHV DTU 电话短信方案（2026-05-10 补充）

### 11.1 新购买模块与结论

本次购买/咨询的模块信息重点如下：

```text
V100C / Air780EHV DTU 固件
支持任务和数据模板代写
示例 1：服务器下发 JSON 后主动呼出电话
示例 2：DTU 固件发送短信测试
重要限制：默认配套物联网卡通常只支持流量，不支持打电话和发短信；如需电话/短信，必须插入自己的普通手机 SIM 卡。
```

结合当前工程，结论是：

```text
DTU 可以作为 Board B 后面的 4G 电话/短信执行器；
WS63 不负责蜂窝协议栈，只在跌倒发生时通过 UART 给 DTU 发一行 JSON；
DTU 的 Lua 任务解析 JSON 后调用 cc.dial() 或短信 API。
```

也就是说，户外化后的报警链路可以变成：

```text
Board A：MPU6050 + TinyML 跌倒检测
    -> SLE 发送 0x05
Board B：SLE Client 收到 0x05
    -> 本地蜂鸣器 / WS2812B 报警
    -> UART 发送 JSON 到 V100C/Air780EHV DTU
DTU：解析 JSON
    -> 4G 普通手机卡呼叫家属 / 发送短信 / 后续也可上云
家属手机
    -> 接到电话或短信
```

这个方案解决了 Wi-Fi 演示版的核心不足：**佩戴者在户外时不再依赖电脑、局域网或旁边手机热点，只依赖蜂窝网络覆盖和 SIM 卡能力。**

### 11.2 与当前 WS63 工程的接入点

仍然沿用当前已经验证的跌倒信号入口：

```text
application/samples/my_demo/fall_detect/src/sle_client_task.c
```

当 SLE Client 收到：

```c
data->data[0] == 0x05
```

当前已经做了：

```text
1. 本地声光报警
2. ACK 回写 0x06
3. Wi-Fi 网关 fall_alert_gateway_post_fall(data->data[0])
```

下一步增加 4G DTU 时，不要推翻现有架构，只增加一个并行出口：

```c
fall_alert_4g_dtu_post_fall(data->data[0]);
```

建议新增文件：

```text
application/samples/my_demo/fall_detect/src/fall_alert_4g_dtu.c
```


这样比赛现场仍可使用 Wi-Fi + PushPlus，后续户外版再打开 DTU UART 出口，两个通道互不冲突。

### 11.3 WS63 到 DTU 的串口协议

第一版协议建议使用换行结束的 JSON，原因是调试简单，PC 串口助手也能直接模拟。

最小呼叫命令：

```json
{"cmd":"call","phone":"13800138000"}
```

串口实际发送时必须带换行：

```text

```

后续可扩展为跌倒报警事件：


### 11.4 DTU 侧 Lua 任务如何从 UART 获取 WS63 JSON（已修正为银尔达 DTU API）

卖家给的电话 demo 是从服务器下行通道取数据：

```lua
local ndata = PronetGetRecChAndDel(1)
local j = json.decode(ndata)
if j and type(j) == "table" and j.cmd and j.phone then
    if j.cmd == "call" then
        outgoing_number = j.phone
        makeCall()
    end
end
```

要接 WS63，需要把数据源从服务器下行改成 UART 接收。最开始从合宙 LuatOS 底层能力出发，可以想到 `uart.setup()` / `uart.on()` / `uart.read()`；但结合银尔达 Air780 系列 API 手册后，**在银尔达 DTU 固件里应优先使用银尔达封装的串口任务 API**：

```lua
local UART_ID = 1

UartStopProRecCh(1)

while true do
    local data = UartGetRecChAndDel(UART_ID)
    if data then
        -- 缓存到 rxbuf，按 \n 切行，json.decode(line)
        -- 若 cmd == "call" 或 "fall_alert"，调用 cc.dial(0, phone)
    end
    sys.wait(100)
end
```

修正原因：

- 银尔达 DTU 固件内部本身会处理串口透传。
- 用户任务如果想自己读取串口数据，需要先调用 `UartStopProRecCh(1)`，停止 DTU 内部自动处理串口接收数据。
- 然后用 `UartGetRecChAndDel(id)` 读取串口缓存。
- 如果需要从 DTU 向外部 MCU 回发数据，可以用 `UartSetSendCh(id, s)`。

API 依据：

- 银尔达 Air780 系列 API 手册给出了 `UartStopProRecCh()`、`UartGetRecChAndDel()`、`UartSetSendCh()`。
- OpenLuat `cc` 通话控制模块提供 `cc.init()`、`cc.dial()`、`cc.hangUp()`、`cc.accept()`、`cc.lastNum()` 等接口。

因此从能力上判断：**V100C 可以通过串口获取 WS63 发来的 JSON，再触发电话/短信。**

当前已经确认的关键参数：

```text
V100C 外部 RXD/TXD 对应银尔达任务 API 串口 ID：1
读取函数：UartGetRecChAndDel(1)
发送函数：UartSetSendCh(1, s)
```

本次补充依据：

```text
V100C 文档：https://yinerda.yuque.com/yt1fh6/4gdtu/ey2rvdi2n9g162bu
Air780 系列 API 手册：https://yinerda.yuque.com/yt1fh6/4gdtu/ngp5mg9s7uavzhdv
```

需要到货后实测或按卖家工具确认的点：

| 项目 | 当前结论 | 建议验证方法 |
| --- | --- | --- |
| 二次开发能力 | V100C 文档写明支持二次开发、支持固件定制 | 用卖家工具确认任务下发/烧录流程 |
| 外部 UART ID | 已确认使用 `UartGetRecChAndDel(1)` | 到货后仍建议用 PC 串口助手复测一次 |
| UART 电平 | V100C 文档明确为 3.3V TTL | 可以与 WS63 直连 TX/RX/GND，但必须共地 |
| SIM 卡是否支持电话/短信 | 物联网卡常常不能打电话 | 插自己的普通手机卡测试 |
| 4G 信号与供电是否稳定 | 通话瞬时电流大，供电不足会重启 | 独立 5V/12V 电源，接 4G 天线 |

## 12. 小白版完整解释：从“跌倒”到“手机报警”到底发生了什么

本节把前面已经完成和准备完成的事情重新用入门视角梳理一遍，目的是让没有接触过嵌入式、DTU、云推送的人也能看懂。

### 12.1 整个系统解决的实际问题

本项目不是单纯让开发板亮灯，而是解决一个真实场景：

```text
老人 / 运动者 / 户外佩戴者摔倒
    -> 设备自动判断这是跌倒
    -> 设备本地立刻蜂鸣和亮灯
    -> 同时把报警消息发给手机端
    -> 家属或监护人及时知道有人可能摔倒
```

目前系统分成两个层次：

| 层次 | 作用 | 当前状态 |
| --- | --- | --- |
| 比赛演示层 | 让评委现场看到“检测到跌倒 -> 手机收到通知” | 已通过 Wi-Fi + PushPlus 跑通 |
| 产品化户外层 | 让佩戴者不在电脑/路由器旁边也能报警 | 设计为 V100C/Air780EHV 4G DTU + 普通手机 SIM |

### 12.2 为什么需要两块 WS63 板

当前工程采用两块 WS63：

```text
Board A：佩戴端 / 检测端
    负责 MPU6050 采样、TinyML 推理、判断是否跌倒

Board B：报警网关端 / 接收端
    负责接收 Board A 的 SLE 跌倒消息，并扩展 Wi-Fi 或 4G 报警
```

这样设计的好处是职责清楚：

- Board A 专注“有没有跌倒”，实时性更强。
- Board B 专注“怎么报警出去”，可以接 Wi-Fi、4G、后端、手机通知。
- 跌倒信号只需要用一个简单字节传过去，当前工程中就是 `0x05`。

### 12.3 SLE 在这里做什么

SLE 可以理解为开发板之间的近距离无线通信方式。它在本项目中的作用是：

```text
Board A 判断跌倒
    -> 用 SLE 发一个 0x05 给 Board B
Board B 收到 0x05
    -> 认为发生跌倒
    -> 本地报警
    -> 远程报警
```

在工程代码里，最重要的判断点是：

```text
application/samples/my_demo/fall_detect/src/sle_client_task.c
```

当 Client 收到：

```c
data->data[0] == 0x05
```

就说明 Board A 发来了跌倒报警。

### 12.4 Wi-Fi + PushPlus 这条路已经做了什么

比赛演示版先走 Wi-Fi，是因为它最容易在现场稳定展示：

```text
Board A 检测跌倒
    -> SLE 发送 0x05
Board B 收到 0x05
    -> 本地蜂鸣器 / WS2812B 红灯报警
    -> 通过 Wi-Fi 向电脑后端 POST 一段 JSON
Python 后端
    -> 校验 token
    -> 做限流，防止重复刷屏
    -> 调 PushPlus
手机微信
    -> 收到跌倒报警通知
```

这条链路中的关键文件：

| 文件 | 作用 |
| --- | --- |
| `fall_alert_gateway.c` | Board B Wi-Fi 上报任务 |
| `fall_alert_gateway_config.h` | Wi-Fi 名称、密码、服务器 IP、token 配置 |
| `sle_client_task.c` | 收到 `0x05` 后触发远程报警 |
| `tools/fall_alert_backend_demo.py` | 电脑端 Python 后端 |
| `tools/fall_alert_backend.env.example` | 后端环境变量模板 |

这条路的优点：

- 已经跑通，适合比赛现场演示。
- 手机端能真实收到通知。
- 不需要短信签名和单位资质。

这条路的限制：

- Board B 附近必须有 Wi-Fi 或手机热点。
- 后端需要运行在电脑或服务器上。
- 如果佩戴者在户外远离电脑和 Wi-Fi，仅靠这条路不够。

### 12.5 什么是 DTU

DTU 可以理解为“帮普通单片机上网的通信盒子”。

更直白地说：

```text
普通 MCU / WS63：
    会采集传感器、会判断跌倒，但不会自己打电话、发短信、上 4G 网络。

DTU：
    里面有 4G 模块、SIM 卡、天线、固件。
    MCU 只要通过串口发一段数据给 DTU，DTU 就负责把数据通过 4G 发出去，或者执行电话/短信任务。
```

因此 DTU 在本项目中的角色是：

```text
WS63：我检测到跌倒了，这是报警 JSON。
DTU：我收到 JSON 了，我来用 4G 网络打电话或发短信。
```

这能大幅降低 WS63 端开发难度，因为 WS63 不需要自己维护蜂窝网络、SIM 卡注册、电话呼叫状态等复杂逻辑。

### 12.6 为什么选择 V100C / Air780EHV

根据银尔达 V100C 文档，V100C 具备这些关键能力：

- 基于合宙 `Air780EHV`。
- 支持 Cat.1 4G 全网通。
- 支持外置 SIM 卡。
- 支持 1 路 TTL 串口。
- 串口电平是 `3.3V`。
- 支持 `5~36V` 供电，测试时建议 `5~12V`、`10W` 级别电源。
- 支持银尔达 DTU 透传固件。
- 支持二次开发和固件定制。
- 支持 TTS 和 MIC。

这些点对应到本项目就是：

| V100C 能力 | 对本项目的意义 |
| --- | --- |
| 4G Cat.1 | 户外也能联网 |
| SIM 卡 | 可用普通手机卡拨打电话/发短信 |
| 3.3V TTL 串口 | 可以和 WS63 直接 TX/RX/GND 连接 |
| DTU 固件 | 不用从零写 4G 协议栈 |
| 二次开发任务 | 可以写 Lua 任务解析 WS63 发来的 JSON |
| 5~12V 供电 | 适合独立供电，避免 4G 峰值电流导致重启 |

### 12.7 V100C 与 WS63 怎么通信

它们之间不是用 Wi-Fi，也不是用 SLE，而是用最普通、最稳定的串口 UART。

接线如下：

```text
WS63 Board B TX  -> V100C RXD
WS63 Board B RX  <- V100C TXD
WS63 Board B GND -> V100C GND
```

注意：

- TX 接对方 RX，RX 接对方 TX。
- GND 必须共地，否则信号没有共同参考点。
- V100C 串口是 3.3V TTL，可以和 WS63 直接连接。
- V100C 不能用 WS63 的 3.3V 供电，要单独供电。

### 12.8 WS63 发给 V100C 的数据长什么样

为了调试简单，第一版用“一行 JSON”：

```json
{"cmd":"fall_alert","phone":"13800138000","device":"ws63-fall-client-001","payload":5}
```

串口实际发送时要加换行：

```text
{"cmd":"fall_alert","phone":"13800138000","device":"ws63-fall-client-001","payload":5}\r\n
```

字段含义：

| 字段 | 含义 |
| --- | --- |
| `cmd` | 告诉 DTU 要做什么，`fall_alert` 表示跌倒报警 |
| `phone` | 要拨打或发送短信的手机号 |
| `device` | 设备编号，方便后端或日志区分设备 |
| `payload` | 原始跌倒字节，当前是 `5`，对应 SLE 的 `0x05` |

### 12.9 V100C DTU 任务怎么读串口

银尔达 Air780 系列 API 手册提供了串口相关 API：

```lua
UartStopProRecCh(on)
UartGetRecChAndDel(id)
UartSetSendCh(id, s)
```

在本项目中已经确认：

```text
V100C 外部 RXD/TXD 对应串口 ID：1
读取函数：UartGetRecChAndDel(1)
```

所以 DTU 任务流程是：

```text
1. 调用 UartStopProRecCh(1)
   让 DTU 内部不要自动处理串口数据，把串口数据交给我们的任务。

2. 循环调用 UartGetRecChAndDel(1)
   从串口缓存中取出 WS63 发来的字符串。

3. 按 \n 分包
   因为串口是一串连续字节，需要用换行判断“一条 JSON 到这里结束”。

4. json.decode()
   把 JSON 字符串解析成 Lua table。

5. 判断 cmd 和 phone
   如果 cmd 是 call 或 fall_alert，并且 phone 是字符串，就执行拨号。

6. 调用 cc.dial(0, phone)
   让 Air780EHV 发起电话呼叫。
```

仓库里的参考任务文件：

```text
tools/v100c_uart_call_task.lua
```

这个脚本已经改成银尔达 DTU 固件专用版本，核心逻辑就是 `UartStopProRecCh(1)` + `UartGetRecChAndDel(1)`。

### 12.10 DTU 电话/短信方案与 Wi-Fi 方案的关系

两条路不是互相替代，而是分工不同：

| 路径 | 适合场景 | 优点 | 缺点 |
| --- | --- | --- | --- |
| Wi-Fi + PushPlus | 比赛演示、实验室联调 | 已跑通，手机可收微信通知 | 依赖 Wi-Fi/电脑/服务器 |
| V100C DTU + 电话/短信 | 户外佩戴、产品化 | 不依赖电脑和局域网 | 需要普通 SIM 卡、4G 信号、稳定供电 |

推荐比赛展示顺序：

```text
第一步：展示 Board A 跌倒检测和 Board B 本地声光报警。
第二步：展示 Wi-Fi + PushPlus，手机微信收到报警。
第三步：讲解 4G DTU 户外化方案；如果模块调通，再现场展示电话拨号。
```

这样最稳：即使 DTU 到货调试不顺，比赛核心闭环也已经有 Wi-Fi + PushPlus；如果 DTU 成功，项目完整度会更高。

### 13.3 接线方式

WS63 Board B 与 V100C：

```text
WS63 GPIO_15 / UART1_TX  -> V100C RXD
WS63 GPIO_16 / UART1_RX  <- V100C TXD
WS63 GND                 -> V100C GND
```

V100C 供电：

```text
V100C VIN/GND -> 独立 5~12V 电源，建议 10W 级别
```

不要从 WS63 的 3.3V 给 V100C 供电。V100C 的串口电平是 3.3V TTL，因此信号可以直接接，但供电必须独立。

### 13.4 Board B 代码流程

在 `sle_client_task.c` 中已经接入：

```c
#include "fall_alert_4g_dtu.h"
```

初始化阶段：

```c

```

收到跌倒字节时：

```c

    fall_alert_set(true, 0);

}
```

也就是说，Board B 收到 `0x05` 后会同时走三条路：

```text
1. 本地蜂鸣器 + WS2812B 红灯
2. Wi-Fi HTTP -> Python 后端 -> PushPlus 微信通知
3. UART1 JSON -> V100C DTU -> 电话/短信
```

### 13.5 为什么不用在 SLE 回调里直接写很复杂的逻辑

SLE 通知回调属于通信链路的关键路径，不适合做耗时操作。因此 DTU 发送采用“投递事件 + 后台任务”的模式：

```text
SLE 回调：
    只记录 payload、event_count，并置位 g_dtu_alert_pending

fall_4g_dtu 后台任务：
    看到 pending 后判断冷却时间
    拼接 JSON
    调用 uapi_uart_write() 发送到 V100C
```

这样做的好处：

- SLE 回调更短，不容易阻塞无线协议栈。
- 后续如果要增加短信、定位、重试，也可以继续放在后台任务中。
- Wi-Fi 网关和 4G DTU 出口互不影响。

### 13.6 WS63 发给 V100C 的 JSON

Board B 串口发送的数据格式：

```json
{"cmd":"fall_alert","phone":"YOUR_PHONE_NUMBER","device":"ws63-fall-client-001","payload":5,"event_count":1}
```

实际 UART 末尾会带：

```text
\r\n
```

V100C 侧 `tools/v100c_uart_call_task.lua` 会按行解析 JSON：

```text
收到一行 JSON
    -> json.decode()
    -> cmd == "fall_alert"
    -> 取 phone
    -> cc.dial(0, phone)
```
