# 系统实时性·可靠性·星闪优势量化分析

本文对跌倒检测系统做一次严谨的工程分析，回答三个问题并尽量给出量化数据：

1. **实时性**如何？从传感器到报警，时间花在哪里？
2. **可靠性**如何？误报怎么压、链路怎么保、有哪些薄弱点？
3. 有没有**突出星闪(SLE)通信的优势**？如何体现？还差什么？

## 0. 分析方法与数据来源（先说清楚，保证严谨）

量化分析最怕「拍脑袋数字」。本文的每个数字按来源分三类，并明确标注：

| 标记 | 含义 |
| --- | --- |
| 〔代码〕 | 直接来自源码中的常量 / 配置，确定无误 |
| 〔推导〕 | 由代码常量按确定逻辑推算得出 |
| 〔规格〕 | 来自芯片 / 协议规格或仓库既有文档 |

## 1. 实时性分析

### 1.1 数据通路与时间预算表

系统是一条「精准定时采样 → 双任务流水线 → 路径 B 判定 → NN 复核 → 发报警」的处理链。逐环节拆解：

| 环节 | 时间 | 来源 | 说明 |
| --- | --- | --- | --- |
| 单个采样点 I²C 读取 | ≈ 0.4–0.5 ms | 〔推导〕 | 400kHz I²C，1 字节寄存器地址 + 14 字节数据 |
| 硬件采样节拍 | **5 ms（200 Hz）** | 〔代码〕 | `SAMPLE_PERIOD_US = 5000`，硬件 timer 1 中断触发，节拍信号量唤醒采样任务 |
| 采样任务优先级 | `osPriorityAboveNormal` | 〔代码〕 | 高于推理/主判定任务，保证 5 ms 节拍不被推理阻塞 |
| 样本队列深度 | 128 | 〔代码〕 | `IMU_QUEUE_DEPTH = 128`（可缓冲 640 ms 推理耗时期间的样本积压） |
| 等效喂样率 | **200 Hz**，与模型一致 | 〔推导〕 | 硬件 timer 直接驱动，无 `osDelay` 抖动 |
| 首个 NN 窗口填满 | **600 × 5 ms = 3.0 s** | 〔推导〕 | `EI_CLASSIFIER_RAW_SAMPLE_COUNT = 600`，2 通道幅值特征 |
| 路径 B 触发判定 | 每个新样本 | 〔代码〕 | `Fall_Algo_Process()` 每帧调用，状态机 IDLE → FREEFALL → IMPACT_WAIT → POST_IMPACT |
| 路径 B 最快确认时间 | **≈ 1.57 s** | 〔推导〕 | 失重 ≥14 样本(70 ms) + 等冲击 ≤200 样本(1 s) + 沉降 100 样本(0.5 s) + 静止窗口 200 样本(1 s)，路径走最短分支约 (14+1+100+200)·5 ms（注：等冲击若立刻发生只需 1 帧） |
| NN 触发模式 | **事件驱动（非周期）** | 〔代码〕 | 只在路径 B 状态机确认跌倒(`status == 1`)的那一刻调用一次 `EI_Fall_Classify()` |
| 单次 NN 输入数据量 | **1200 floats = 4.8 KB** | 〔推导〕 | 环形缓冲展开为 600 × 2 floats 连续窗口 |
| 单次 `run_classifier()` 计算 | 未知 | 〔未实测〕 | Flatten DSP（均值/方差/RMS 等标量统计） + 极小 NN（arena 仅 4192 B） |
| 报警 SLE Notify 单向送达 | ≈ 6–12.5 ms | 〔推导〕 | 见第 3 章，连接间隔决定 |
| 报警后冷却 | **3 s** | 〔代码〕 | `FALL_DETECT_COOLDOWN_MS = 3000`。序列检测器每次跌倒只确认一次、不会连发，3 s 只用于挡住"跌倒后续抖动"造成的二次误报 |

### 1.2 关键修复：精准定时双任务管线（旧版"喂样率 100Hz≠模型 200Hz"问题已闭环）

`main_task.c` 顶部注释（行 40–47）总结了这次重构的动机：

> `osDelay` 的分辨率只有 10 ms 且有抖动，无法胜任 5 ms 节拍。把"采样"和"推理"拆到两个任务，中间用队列缓冲，这样 `run_classifier` 一次上百 ms 的耗时不会拖慢采样节拍，模型仍能拿到间隔恒定的样本序列。

实现要点（全部〔代码〕）：

- **硬件 timer 1 中断**：`SAMPLE_PERIOD_US = 5000`，中断回调只 `osSemaphoreRelease(g_tick_sem)`，不读 I²C（I²C 是阻塞 API，不能在中断里跑）、不重载定时器（避免与共用 timer1 的软定时器并存时 cycle 下溢）。
- **采样任务 `ImuSampler`**（`osPriorityAboveNormal`，4 KB 栈）：每个节拍先重载定时器，再读 MPU6050 6 轴，入队 `g_imu_queue`。队列满则丢弃并自增 `g_drop_count`（稳态下应恒为 0，状态监控里实时打印）。
- **主任务 `FallTask`**（`osPriorityNormal`，32 KB 栈）：阻塞出队 → `EI_Fall_Push` 写 NN 环形缓冲 → 算 |acc|/|gyro| 监控值 → `Fall_Algo_Process` 跑路径 B → 触发后调用 NN 复核。

效果：采样节拍由硬件 timer 决定、完全独立于推理耗时；NN 推理期间采样不丢节拍（最多在队列里积压，128 槽位足以撑过整次推理）。**旧文档里"主循环 osDelay(10) 把喂样率压到 100Hz"以及"推理同步阻塞会卡掉采样"这两个发现均已不再适用。**

### 1.3 单次推理的数据量与触发频率

| 维度 | 数值 | 备注 |
| --- | --- | --- |
| NN 输入窗口长度 | 3.0 s | 600 样本 × 5 ms |
| NN 输入通道 | 2（`\|acc\|` 幅值 milli-g、`\|gyro\|` 幅值 centi-dps） | 朝向无关特征，与 `make_features.py` 训练时口径完全一致 |
| 单次推理输入字节数 | **4800 B (1200 floats)** | `EI_CLASSIFIER_DSP_INPUT_FRAME_SIZE = 1200`，固定 |
| NN 环形缓冲常驻 | 4800 B + 4800 B 展开窗口 = 9.6 KB | `g_ring` + `g_window`，全静态 |
| 推理触发频率 | **事件驱动**，非周期 | 仅路径 B 确认跌倒那一刻触发一次 |
| 两次推理最小间隔 | ≥ 3 s | 报警/否决均不会立刻再触发：报警进入 3 s 冷却；否决时路径 B 状态机已自然 reset，需重新走完"失重→冲击→静止" |

注意：`model_metadata.h` 里定义了 `EI_CLASSIFIER_SLICES_PER_MODEL_WINDOW = 4`、`SLICE_SIZE = 150`（每 750 ms 一片），那是给 `run_classifier_continuous` 用的滚动推理切片大小。**当前代码用的是 `run_classifier`（整窗、按需）**，所以这个切片大小目前未生效。若以后改为纯 NN 兜底、想做"每 750 ms 自动推一次"的滚动判定，切到 `run_classifier_continuous` 即可，SDK 内部会维护切片状态。

### 1.4 端到端延迟拆解

从「跌倒动作完整进入数据缓冲」到「客户端收到报警」：

```
T_端到端 ≈ T_路径B 序列确认 (≈ 1.5–2 s) + T_NN 复核 (单次推理耗时, 未实测)
        + T_SLE 单向送达 (≈ 6–12.5 ms) + T_客户端处理
```

- 主导项是**路径 B 的序列确认时间**：状态机要观察"失重 → 冲击 → 沉降 → 静止"四段齐全，最短约 1.57 s（沉降 + 静止两段占大头）。这是物理判据本身的代价、不是软件瓶颈。
- **SLE 无线传输只占约 6–12.5 ms，在端到端延迟里占比 < 1%**，不是瓶颈。
- 〔未实测〕的只剩 NN 推理耗时一项；建议在 `ei_fall.cpp:120` 的 `run_classifier` 前后用 `uapi_systick_get_ms()` 取差打印，几行代码即可补上量化数字。

### 1.5 实时性结论

- 本系统是**软实时**监测系统，不是硬实时：没有严格截止期保证，但采样侧已经达到"硬件定时 + 高优先级任务"的稳定性。
- 端到端延迟主要由**路径 B 序列确认（≈ 1.5–2 s）**决定，量级亚秒~2 秒，符合"跌倒后及时报警"的产品诉求（不需要毫秒级响应）。
- **无线链路本身很快（~12.5 ms 内）、不是瓶颈**——这点对第 3 章「星闪优势」的判断很关键。
- 历史上"喂样率被 osDelay 拖到 100Hz"与"推理同步阻塞采样"两个问题，已被 200Hz 硬件 timer + 双任务+队列架构彻底解决；当前剩下的唯一未实测项是单次推理绝对耗时。

## 2. 可靠性分析

### 2.1 误报抑制：路径 B 序列状态机 + NN 复核否决

跌倒检测最怕误报。当前系统**不**靠"模型概率门限 + 多窗确认"那一类纯统计判据，而是用**确定性物理序列**做主判，再用 NN 做事后复核否决。两条路径职责分明：

#### 路径 B（主判，`fall_algo.c`）——四项物理判据齐全才确认

真实跌倒有固定物理特征序列；状态机 `IDLE → FREEFALL → IMPACT_WAIT → POST_IMPACT` 逐段验证，**四项都满足才返回 1**（〔代码〕，参数按 200Hz 采样、模块腰部佩戴调校）：

| 判据 | 阈值 | 物理含义 | 能挡掉的误报 |
| --- | --- | --- | --- |
| ① 自由落体段 | \|acc\| < 0.75 G 持续 ≥ 14 样本(70 ms)，且 ≤ 150 样本(750 ms) | 失重，跌倒固有起点 | 轻拿轻放（无失重）、长时间失重（异常） |
| ② 冲击段 | 失重结束后 ≤ 200 样本(1 s)内 \|acc\| > 2.20 G | 撞地瞬间冲击峰 | 轻放（有失重无冲击） |
| ③ 硬冲击门槛 | 冲击峰值 ≥ **4.0 G** | 失控撞地 vs 肌肉减速 | **快速蹲下/用力坐下**（实测峰 ≤ 3.1 G） |
| ④ 冲击后静止 | 跳过 100 样本沉降期后，再观察 200 样本（1 s）窗口；其中 \|acc\| ∈ [0.6, 1.4] G 的样本占比 ≥ 50% | 人躺地不动 | 剧烈摇晃（冲击后仍在动） |
| ⑤ 倾角判据 | 冲击前后重力方向夹角 ≥ **45°** | 躯干由直立变倾倒 | **原地起跳落地**（躯干仍直立，实测真实跌倒 tilt ≥ 73°） |

实测峰值对照（来源：板上 `[Fall]` 日志）：
- 真实跌倒：impact ≥ 5.3 G，tilt ≥ 73°
- 快速蹲下/坐下：impact ≤ 3.1 G（被 ③ 否决）
- 原地起跳落地：impact 可能很高但 tilt 接近 0°（被 ⑤ 否决）

每次事件无论确认还是否决，都打印 `impact / tilt / ffmin / still%` 四项实测特征，便于现场据实测值微调阈值。

#### NN 复核否决（`ei_fall.cpp` + `main_task.c:251`）——只用于"撤回报警"

路径 B 已经确认后，主任务调用 `EI_Fall_Classify()`：

- NN 输入：环形缓冲里"截至此刻最近 3 s"的 |acc|/|gyro| 幅值序列，与训练数据口径一致（朝向无关，与传感器佩戴方向解耦）。
- 否决规则（〔代码〕`NN_VETO_NORMAL_PCT = 95`）：**仅当 NN 以 ≥ 95% 置信度判为 normal 才否决该次报警；NN 同意 / NN 不可用 / NN 置信度不足，一律以路径 B 为准报警。**
- 这是一个**保守**设计：优先不漏报。`main_task.c:36` 的注释解释了 95 这个值是怎么选的——板上硬真摔 NN 输出 fall=100%、normal=0%，偏软的摔约 50/50；阈值放 95 既不会误否决真摔，又能在路径 B 偶然误触发且 NN 高置信判 normal 时挡掉误报。
- 路径 B 在每帧调用之后还有 **3 s 冷却**（`FALL_DETECT_COOLDOWN_MS`），防止跌倒后续抖动造成的二次报警。

#### 数据预处理稳健性

| 机制 | 实现 |
| --- | --- |
| 传感器低通 | MPU6050 配 ~44 Hz 数字低通（DLPF），抑制毛刺 |
| 陀螺仪零偏校准 | 开机做 128 次采样的均值校准 |
| 朝向无关特征 | NN 输入只取 \|acc\|/\|gyro\| 幅值（标量），消除"佩戴朝向影响" |
| 量纲一致 | 单位 milli-g / centi-dps，部署时与 `make_features.py` 训练 CSV 完全一致 |

### 2.2 内存与系统稳定性

| 项 | 配置 | 可靠性意义 |
| --- | --- | --- |
| Edge Impulse 内存池 | 全静态分配，无堆 | 与系统堆隔离，无运行期堆碎片 |
| 内存分配 | 重写 `ei_malloc/ei_free`，全静态 | 池耗尽可被检测并打印，不会静默崩 |
| NN 环形缓冲 + 展开窗口 | 静态 2 × 1200 float = 9.6 KB，16 字节对齐 | 编译期确定，无动态增长 |
| TFLite 运行内存 | arena 仅 4192 B | 模型极小，内存压力低 |
| 模型句柄构造 | placement-new 显式构造 | 规避 WS63 不跑全局构造函数的坑 |
| 采样任务栈 | 4 KB | 中断回调只放信号量，任务上下文做 I²C，避免中断里阻塞 |
| 主任务栈 | 32 KB | C++ 推理栈深可控 |
| C++ 运行时 | `-fno-exceptions -fno-rtti` | 关异常，避免不可控展开 |
| 队列丢帧监控 | `g_drop_count` 每秒打印 | 稳态下应恒为 0；非零即可见 |

全链路**静态分配**是这套系统可靠性的重要基础：运行期不依赖动态堆，不会因碎片化随机失败。

### 2.3 通信链路可靠性

SLE 链路做了完整的「断连自愈 + 送达确认」〔代码 `sle_server_task.c` / `sle_client_task.c`〕：

| 机制 | 实现 | 效果 |
| --- | --- | --- |
| 连接守卫 | 未连接时 `sle_send_fall_alert` 直接丢弃 | 不向空连接发包 |
| 服务端断连自愈 | 断开回调里 `sle_start_announce` 重开广播 | 客户端能重新搜到 |
| 客户端断连自愈 | 断开回调里 `sle_start_seek` 重新扫描重连 | 自动恢复连接 |
| 监督超时 | 32 s（`conn_supervision_timeout = 0x0C80`） | 容忍短时干扰，不轻易掉线 |
| 连接潜伏期 | 0（`conn_max_latency = 0`） | 每个连接事件都活跃，响应最快 |
| 应用层 ACK | `0x05` 告警 → 客户端回 `0x06` → 服务端确认 | 报警送达可验证（业务级闭环） |
| 链路层确认 | `write_cfm_cb` 回调 | ACK 包送达有链路层确认 |
| 握手通知 | 连接建立即发 `0x01` | 不依赖客户端 CCCD 写，重连即可用 |

### 2.4 已知薄弱点（如实列出）

严谨分析必须包含弱点。以下是当前主分支下仍存在的问题：

1. **断连瞬间的跌倒会丢失且被静默**：若跌倒发生时 SLE 未连接，`sle_send_fall_alert` 返回失败，但 `main_task.c` 仍照常进入 3 s 冷却 —— 这次跌倒既没发出去、又被冷却压制。建议：发送失败时不进冷却，或加一个待发队列在重连后补发。
2. **Notify 无应用层重传**：一次 Notify 失败不会自动重发，仅靠 SLE 链路层确认。
3. **单次推理绝对耗时仍未实测**：EI 计时函数未适配 WS63 已被移除；建议用 systick 在 `run_classifier` 前后取差打印，几行即可。
4. **NN 在"偏软摔"上区分力弱**：板上日志显示硬真摔 NN 输出 fall=100%，偏软摔约 50/50；目前用 95% 否决阈值保守处理，但意味着 NN 的"复核能力"在临界场景下其实没怎么发挥。建议扩充偏软摔数据集并重训。
5. **MAC 地址硬编码、单客户端**：`g_sle_conn_hdl` 用 `0xFFFF` 哨兵，只支持 1 个客户端；服务端/客户端 MAC 写死，只能这对板子配对，不可规模化。
6. **路径 B 阈值是按"腰部佩戴"调校的**：胸前/腕部佩戴时冲击峰、倾角变化会不同，阈值需要重新调（每次事件打印的 `[Fall] impact/tilt/ffmin/still%` 就是为此而设）。
7. **队列丢帧不会自动告警**：`g_drop_count > 0` 当前只打印，没有触发任何动作；稳态下不会非零，但若 I²C 卡死/推理异常拖慢主任务，会静默丢样本。

## 3. 星闪(SLE)通信优势分析

### 3.1 SLE vs BLE 规格对比

| 对比项 | BLE | SLE（星闪） |
| --- | --- | --- |
| 连接间隔粒度 | 1.25 ms | **0.125 ms（125µs）** |
| 连接间隔下限 | 7.5 ms | **0.125 ms** |
| 理论速率 | ~2 Mbps | ~12 Mbps |
| 时延（规格量级） | 毫秒级 | 亚毫秒级 |

> 速率/时延的概览数据与仓库 `docs/05-通信协议/SLE_vs_BLE.md` 一致。连接间隔粒度 125µs 由本工程 SLE SDK 源码直接确认（`sle_speed_server_adv.c` 注释「单位125us」）。

SLE 的核心优势在于**连接调度粒度比 BLE 细一个量级**：BLE 最快也只能 7.5 ms 一个连接事件，SLE 可以低到 125 µs。

### 3.2 本工程实际配置的 SLE 参数

来自 `sle_speed_server_adv.c` 的生效函数 `sle_set_default_announce_param()`〔代码〕：

| 参数 | 配置值 | 换算 |
| --- | --- | --- |
| `conn_interval_min` | 0x0032 = 50 | 50 × 125µs = **6.25 ms** |
| `conn_interval_max` | 0x0064 = 100 | 100 × 125µs = **12.5 ms** |
| `conn_max_latency` | 0x0000 | 0，无潜伏期 |
| `conn_supervision_timeout` | 0x0C80 = 3200 | 3200 × 10ms = **32 s** |
| `announce_interval` | 0xC8 = 200 | 200 × 125µs = **25 ms** 广播间隔 |

### 3.3 量化：本工程 SLE 链路延迟 vs BLE 等效配置

一条 Notify 在下一个连接事件发出，因此**单向送达延迟 ≤ 一个连接间隔**：

| 链路 | 连接间隔 | 单向通知延迟（最坏） | 相对本工程 SLE |
| --- | --- | --- | --- |
| **SLE — 本工程实配** | 6.25–12.5 ms | **≈ 12.5 ms** | 基准 |
| BLE — 仓库示例配置（20–60ms） | 20–60 ms | ≈ 60 ms | 慢约 5× |
| BLE — 规格下限 | 7.5 ms | ≈ 7.5 ms | 接近 |
| SLE — 规格下限 | 0.125 ms | < 1 ms | 快约 12× |

应用层 ACK 往返（`0x05` 发出 → `0x06` 回来）≈ 2 个连接间隔 + 处理 ≈ **13–25 ms**。

**结论**：本工程把 SLE 配在 6.25–12.5 ms，已经比仓库 BLE 示例配置（最坏 60 ms）快约 **5×**；但距离 SLE 规格下限（< 1 ms）还有约 **12×** 的余量没用。

### 3.4 工程「体现」了哪些 SLE 优势，哪些没体现

**已经体现的（是真实优势）：**

- ✅ 打通了完整的 SLE 板间链路：广播 → 扫描 → 连接 → 配对 → MTU 协商 → 服务发现 → SSAP Notify → ACK 回传。
- ✅ 连接间隔 6.25–12.5 ms + `conn_max_latency = 0`：这是**偏向低延迟**的主动选择，告警单向送达最坏 ~12.5 ms，量化上优于 BLE 示例配置约 5×。
- ✅ 断连自愈 + 32 s 监督超时：链路抗短时干扰、能自动恢复。
- ✅ 应用层 ACK 闭环：告警送达可验证。

**尚未体现的（优势没用满）：**

- ⚠️ 没用 SLE 的极低连接间隔（125 µs）：实配 6.25–12.5 ms 偏保守（源码注释说明是为连接稳定性硬编码）。
- ⚠️ 没体现吞吐优势：告警载荷只有 1 字节(`0x05`)，12 Mbps 完全用不上。
- ⚠️ 没有 SLE vs BLE 的同条件实测对比，目前优势是「按参数推导」而非「测出来」。
- ⚠️ **关键**：端到端延迟被路径 B 序列确认（≈ 1.5–2 s）主导，SLE 的 ~12.5 ms 占比 < 1%。即便 SLE 链路再快 10 倍，用户也几乎感知不到差别。**SLE 的低延迟优势在系统层面被"物理判据所需时间"淹没，这是物理判据自身的代价、不是软件可优化项。**

一句话：**SLE 确实用上了、参数也偏低延迟、相对 BLE 有可量化的约 5× 优势；但它既没被推到规格极限，也因为路径 B 物理判据本身要花 1.5–2 s 而无法在端到端层面凸显。**

### 3.5 如何进一步凸显星闪优势（可操作 + 可量化）

要让「星闪优势」从「推导」变成「实测亮点」，建议：

1. **直接测空口延迟**：服务端发 Notify 前翻转一个 GPIO，客户端 `notification_cb` 里翻转另一个 GPIO，用双通道示波器/逻辑分析仪同时抓 —— 直接读出空口延迟（µs 级精度）。
2. **压低连接间隔再测**：把 `conn_interval` 从 0x32/0x64 调到 0x08（1 ms）甚至更低，重测延迟，验证能否逼近亚毫秒。
3. **SLE vs BLE 同条件对比**：用 `MANUAL_SLE_SWITCH` 切到 BLE 路径，相同 1 字节载荷、相同测量方法，做一张 SLE/BLE 延迟对比表。
4. **抗干扰对比**：在 2.4 GHz 强干扰（Wi-Fi 灌包/微波炉）下，各发 N = 1000 次告警，统计送达率，体现 SLE 的抗干扰可靠性。
5. **把测得的数字写进文档**：用实测表格替换本文 3.3 的「推导」标记，让优势可信。

> 端到端延迟的下限被路径 B 的物理判据决定（沉降 + 静止两段共 1.5 s 不可压缩），所以**不要再把"缩短 AI 管线"当作让 SLE 显形的方向** —— 这条路径在重构成路径 B 主判后已经不再是延迟瓶颈的源头。要让 SLE 显形，靠的是上面 1–4 的"链路层直接测量"。

> 上述每一项的**具体操作步骤、代码片段、接线方式、读数方法**，见配套实操手册《[性能测试与 SLE 延迟验证方法](性能测试与SLE延迟验证方法.md)》——照着做就能把本文标〔未实测〕〔推导〕的数字测出来。

## 5. 总体结论

- **实时性**：软实时系统。采样侧已达到"硬件定时 5 ms + 高优先级任务"的稳定喂样，与 NN 模型的 200 Hz 训练频率完全一致。端到端延迟由**路径 B 序列确认（≈ 1.5–2 s）**主导，这是物理判据自身的代价；唯一未实测项是 NN 单次推理绝对耗时（数百毫秒量级，下限受 Flatten DSP + 极小 NN 决定）。单次 NN 推理喂入 1200 floats / 4.8 KB，事件驱动、非周期触发。
- **可靠性**：误报抑制由"路径 B 序列状态机（自由落体 → 冲击 ≥ 4.0 G → 沉降 → 静止 → 倾角 ≥ 45°，五项齐全）+ NN 复核否决（normal ≥ 95% 才否决）"承担，再加 3 s 冷却。内存全静态分配，系统稳定性基础好；SLE 链路有断连自愈和 ACK 闭环。主要薄弱点是"断连瞬间跌倒会丢失且被静默冷却"和"NN 在偏软摔上区分力弱"。
- **星闪优势**：已用上 SLE 并把参数配在偏低延迟档位，相对仓库 BLE 示例配置有可量化的约 **5×** 延迟优势；但未推到规格极限、未做实测对比，且因路径 B 物理判据本身要花 1.5–2 s，SLE 的低延迟在端到端层面无法凸显。第 3.5 节给出了把它「测出来、显出来」的具体路径。
