# 系统实时性·可靠性·星闪优势量化分析

本文对跌倒检测系统做一次严谨的工程分析，回答三个问题并尽量给出量化数据：

1. **实时性**如何？从传感器到报警，时间花在哪里？
2. **可靠性**如何？误报怎么压、链路怎么保、有哪些薄弱点？
3. 有没有**突出星闪(SLE)通信的优势**？如何体现？还差什么？

---

## 0. 分析方法与数据来源（先说清楚，保证严谨）

量化分析最怕「拍脑袋数字」。本文的每个数字按来源分三类，并明确标注：

| 标记 | 含义 |
| --- | --- |
| 〔代码〕 | 直接来自源码中的常量 / 配置，确定无误 |
| 〔推导〕 | 由代码常量按确定逻辑推算得出 |
| 〔规格〕 | 来自芯片 / 协议规格或仓库既有文档 |
| 〔未实测〕 | 当前无法可靠测量，只能定性，**不作为结论依据** |

> **重要前提**：开发日志(`docs/日志/开发日志.md`)记录，Edge Impulse SDK 的计时函数未适配 WS63 平台、已被移除。因此**单次推理的绝对耗时目前没有可信实测值**。仓库早期文档 `SLE_SSAP通知链路.md` 中出现过的 `~3045ms DSP / ~2798ms TFLite / ~5.8s / ~12s` 等数字，来自那个失效的计时函数、且基于已废弃的旧设计（100采样×3轴），**不可作为依据**，本文不沿用。

本文分析的代码基准：

- `application/samples/my_demo/fall_detect/src/main_task.c`（主循环）
- `.../src/ai_model.cpp`（推理封装）
- `.../src/mpu6050.c`（传感器驱动）
- `.../src/sle_server_task.c`（SLE 服务端）
- `.../bt/sle/sle_speed_server/src/sle_speed_server_adv.c`（SLE 连接/广播参数）

## 1. 实时性分析

### 1.1 数据通路与时间预算表

系统是一条「采样 → 攒窗口 → 推理 → 判定 → 发报警」的流水线。逐环节拆解：

| 环节 | 时间 | 来源 | 说明 |
| --- | --- | --- | --- |
| 单个采样点 I²C 读取 | ≈ 0.4–0.5 ms | 〔推导〕 | 400kHz I²C，1字节寄存器地址 + 14字节数据 |
| 主循环周期 | ≈ 10 ms | 〔代码〕 | `osDelay(FALL_DETECT_LOOP_DELAY_MS=10)` 主导 |
| → 等效喂样率 | ≈ **100 Hz** | 〔推导〕 | 每个循环喂 1 个采样点 |
| 首个窗口填满 | 256 × 10ms ≈ **2.56 s** | 〔推导〕 | `EI_CLASSIFIER_RAW_SAMPLE_COUNT=256` |
| 推理触发间隔（稳态） | 64 × 10ms ≈ **640 ms** | 〔推导〕 | 每次滑动 `SLIDE_STEP=64采样点` |
| 单次 `run_classifier()` 计算 | 未知 | 〔未实测〕 | DSP(64点FFT×6轴谱分析)为主，NN 极小(arena 仅 4192 B) |
| 2 窗确认附加延迟 | + 1 个推理周期 ≈ 640 ms（+推理耗时） | 〔代码〕 | `FALL_CONFIRM_WINDOWS=2` |
| SLE Notify 单向送达 | ≈ 6–12.5 ms | 〔推导〕 | 见第 3 章，连接间隔决定 |
| 报警后冷却 | 10 s | 〔代码〕 | `FALL_DETECT_COOLDOWN_MS=10000` |

### 1.2 实时性发现一：喂样率 100 Hz，模型期望 200 Hz

- 模型元数据 `EI_CLASSIFIER_FREQUENCY=200`（200 Hz，5ms/采样点）。〔代码〕
- MPU6050 内部 ODR 也配成了 200 Hz（`SMPLRT_DIV=4` → 1kHz/5）。〔代码〕
- **但主循环 `osDelay(10)` 把实际喂样率压到了约 100 Hz**。〔推导〕

后果：256 个采样点的窗口，模型以为代表 `256/200=1.28 s`，实际却覆盖了 `256/100≈2.56 s` 的真实时间。谱分析(FFT)算出的频率分量会整体偏移约 2×。这是一个**确定存在的实时性/精度偏差**，建议把循环延时改为 5ms、或用传感器中断/FIFO 按 200Hz 取数。

### 1.3 实时性发现二：推理是同步阻塞，会「卡掉」采样

`AI_Feed_And_Predict_6Axis()` 在窗口填满的那一次调用里，**同步**执行 `run_classifier()` 才返回。期间主循环不读 MPU6050。〔代码〕

后果：每个推理周期里，保留的 1152 个旧采样点和随后新采的 64 个采样点之间，存在一段「推理耗时」长的时间空洞，窗口不再是均匀采样。推理越慢，空洞越大，对谱分析输入质量影响越大。

建议：把推理放到独立优先级较低的任务，用消息队列把窗口数据传过去，采样任务保持固定节拍。

### 1.4 端到端延迟拆解

从「跌倒动作完整进入滑动窗口」到「客户端收到报警」：

```
T_端到端 ≈ T_推理 + T_确认(≈640ms + T_推理) + T_SLE(≈12.5ms) + T_客户端处理
```

- 主导项是 **AI 推理管线**：单次推理耗时 + 640ms 的滑窗节拍 + 需要 2 个窗口确认。
- **SLE 无线传输只占约 12.5 ms，在端到端延迟里占比 < 1–2%**，不是瓶颈。
- 〔未实测〕的只有 `T_推理` 一项；建议用 GPIO 翻转 + 逻辑分析仪，或在 `run_classifier()` 前后读 `uapi_systick_get_ms()` 实测补上。

### 1.5 实时性结论

- 本系统是**软实时**监测系统，不是硬实时：没有严格的截止期保证，推理同步阻塞且节拍较慢。
- 端到端延迟主要被 **AI 推理 + 640ms 滑窗节拍 + 2 窗确认** 决定，量级在「亚秒到数秒」。
- **无线链路本身很快（~12.5ms），不是延迟瓶颈**——这点对第 3 章「星闪优势」的判断很关键。
- 两个可量化改进点：喂样率补到 200Hz；推理改异步。

## 2. 可靠性分析

### 2.1 误报抑制：四层防线（关键指标量化）

跌倒检测最怕误报。系统在「模型输出」之外叠加了多层物理与时序约束，全部来自 `ai_model.cpp`〔代码〕：

| 层 | 机制 | 阈值 |
| --- | --- | --- |
| ① 模型概率门限 | `fall_risk` 概率须达标 | ≥ 80%（`FALL_RISK_THRESHOLD_PERCENT`） |
| ② 物理门控 | 冲击+旋转 **或** 失重+冲击 | 加速度峰 ≥1.8g / 自由落体 ≤0.45g / 角速度峰 ≥0.8 |
| ③ 多采样命中 | 单点毛刺不算，需多点满足 | 命中数 ≥ 3（`FALL_GATE_MIN_HIT_SAMPLES`） |
| ④ 连续窗口确认 | 连续多窗都判跌倒才报警 | 连续 2 窗（`FALL_CONFIRM_WINDOWS`） |

只有「模型说是跌倒」**且**「物理特征也像跌倒」**且**「连续 2 个窗口都成立」才会真正报警。这把单纯依赖神经网络（开发日志记录其存在板端 domain mismatch）的误报风险显著压低。报警后还有 **10 s 冷却**，避免一次跌倒被连环触发。

数据预处理侧的稳健性：`sanitize_value()` 拦截 NaN/Inf、`clamp_value()` 限幅；MPU6050 开了 ~44Hz 数字低通滤波抑制毛刺，并在开机做 128 次采样的陀螺仪零偏校准。〔代码〕

### 2.2 内存与系统稳定性

| 项 | 配置 | 可靠性意义 |
| --- | --- | --- |
| AI 专用内存池 | 静态 40 KB（`AI_POOL_SIZE`） | 与系统堆隔离，无运行期堆碎片 |
| 内存分配 | 重写 `ei_malloc/ei_free`，全静态 | 池耗尽可被检测并打印，不会静默崩 |
| 特征缓冲区 | 静态 1536 float = 6 KB | 编译期确定，无动态增长 |
| TFLite 运行内存 | arena 仅 4192 B | 模型极小，内存压力低 |
| 跌倒任务栈 | 32 KB | 独立任务，C++ 推理栈深可控 |
| C++ 运行时 | `-fno-exceptions -fno-rtti` | 关异常，避免不可控展开 |
| 模型句柄构造 | 运行期 placement-new | 规避 WS63 不跑全局构造函数的坑 |

全链路**静态分配**是这套系统可靠性的重要基础：运行期不依赖动态堆，不会因碎片化而随机失败。

### 2.3 通信链路可靠性

SLE 链路做了完整的「断连自愈 + 送达确认」〔代码 `sle_server_task.c` / `sle_client_task.c`〕：

| 机制 | 实现 | 效果 |
| --- | --- | --- |
| 连接守卫 | 未连接时 `sle_send_fall_alert` 直接丢弃 | 不向空连接发包 |
| 服务端断连自愈 | 断开回调里 `sle_start_announce` 重开广播 | 客户端能重新搜到 |
| 客户端断连自愈 | 断开回调里 `sle_start_seek` 重新扫描重连 | 自动恢复连接 |
| 监督超时 | 32 s（`conn_supervision_timeout=0x0C80`） | 容忍短时干扰，不轻易掉线 |
| 连接潜伏期 | 0（`conn_max_latency=0`） | 每个连接事件都活跃，响应最快 |
| 应用层 ACK | `0x05` 告警 → 客户端回 `0x06` → 服务端确认 | 报警送达可验证（业务级闭环） |
| 链路层确认 | `write_cfm_cb` 回调 | ACK 包送达有链路层确认 |
| 握手通知 | 连接建立即发 `0x01` | 不依赖客户端 CCCD 写，重连即可用 |

### 2.4 已知薄弱点（如实列出）

严谨分析必须包含弱点：

1. **断连瞬间的跌倒会丢失且被静默**：若跌倒发生时 SLE 未连接，`sle_send_fall_alert` 返回失败，但 `main_task.c` 仍照常进入 10s 冷却 —— 这次跌倒既没发出去、又被冷却压制 10s。建议：发送失败时不进冷却，或加一个待发队列在重连后补发。
2. **Notify 无应用层重传**：一次 Notify 失败不会自动重发，仅靠 SLE 链路层。
3. **推理同步阻塞**（见 1.3）：推理期间采样中断。
4. **喂样率 100Hz≠模型 200Hz**（见 1.2）：影响推理精度。
5. **MAC 地址硬编码、单客户端**：`g_sle_conn_hdl` 用 `0xFFFF` 哨兵，只支持 1 个客户端；服务端/客户端 MAC 写死，只能这对板子配对，不可规模化。
6. **模型 domain mismatch**：训练用 SisFall、部署用 MPU6050 实测，分布有差异（开发日志已记录），目前靠物理门控补偿。

## 3. 星闪(SLE)通信优势分析

### 3.1 SLE vs BLE 规格对比

| 对比项 | BLE | SLE（星闪） |
| --- | --- | --- |
| 连接间隔粒度 | 1.25 ms | **0.125 ms（125µs）** |
| 连接间隔下限 | 7.5 ms | **0.125 ms** |
| 理论速率 | ~2 Mbps | ~12 Mbps |
| 时延（规格量级） | 毫秒级 | 亚毫秒级 |

> 速率/时延的概览数据与仓库 `docs/05-通信协议/SLE_vs_BLE.md` 一致。连接间隔粒度 125µs 由本工程 SLE SDK 源码直接确认（`sle_speed_server_adv.c` 注释「单位125us」）。

SLE 的核心优势在于**连接调度粒度比 BLE 细一个量级**：BLE 最快也只能 7.5ms 一个连接事件，SLE 可以低到 125µs。

### 3.2 本工程实际配置的 SLE 参数

来自 `sle_speed_server_adv.c` 的生效函数 `sle_set_default_announce_param()`〔代码〕：

| 参数 | 配置值 | 换算 |
| --- | --- | --- |
| `conn_interval_min` | 0x0032 = 50 | 50 × 125µs = **6.25 ms** |
| `conn_interval_max` | 0x0064 = 100 | 100 × 125µs = **12.5 ms** |
| `conn_max_latency` | 0x0000 | 0，无潜伏期 |
| `conn_supervision_timeout` | 0x0C80 = 3200 | 3200 × 10ms = **32 s** |
| `announce_interval` | 0xC8 = 200 | 200 × 125µs = **25 ms** 广播间隔 |

### 3.3 量化：本工程 SLE 链路延迟 vs BLE 等效配置

一条 Notify 在下一个连接事件发出，因此**单向送达延迟 ≤ 一个连接间隔**：

| 链路 | 连接间隔 | 单向通知延迟（最坏） | 相对本工程 SLE |
| --- | --- | --- | --- |
| **SLE — 本工程实配** | 6.25–12.5 ms | **≈ 12.5 ms** | 基准 |
| BLE — 仓库示例配置（20–60ms） | 20–60 ms | ≈ 60 ms | 慢约 5× |
| BLE — 规格下限 | 7.5 ms | ≈ 7.5 ms | 接近 |
| SLE — 规格下限 | 0.125 ms | < 1 ms | 快约 12× |

应用层 ACK 往返（`0x05` 发出 → `0x06` 回来）≈ 2 个连接间隔 + 处理 ≈ **13–25 ms**。

**结论**：本工程把 SLE 配在 6.25–12.5ms，已经比仓库 BLE 示例配置（最坏 60ms）快约 **5×**；但距离 SLE 规格下限（<1ms）还有约 **12×** 的余量没用。

### 3.4 工程「体现」了哪些 SLE 优势，哪些没体现

**已经体现的（是真实优势）：**

- ✅ 打通了完整的 SLE 板间链路：广播 → 扫描 → 连接 → 配对 → MTU 协商 → 服务发现 → SSAP Notify → ACK 回传。
- ✅ 连接间隔 6.25–12.5ms + `conn_max_latency=0`：这是**偏向低延迟**的主动选择，告警单向送达最坏 ~12.5ms，量化上优于 BLE 示例配置约 5×。
- ✅ 断连自愈 + 32s 监督超时：链路抗短时干扰、能自动恢复。
- ✅ 应用层 ACK 闭环：告警送达可验证。

**尚未体现的（优势没用满）：**

- ⚠️ 没用 SLE 的极低连接间隔（125µs）：实配 6.25–12.5ms 偏保守（源码注释说明是为连接稳定性硬编码）。
- ⚠️ 没体现吞吐优势：告警载荷只有 1 字节(`0x05`)，12 Mbps 完全用不上。
- ⚠️ 没有 SLE vs BLE 的同条件实测对比，目前优势是「按参数推导」而非「测出来」。
- ⚠️ **关键**：端到端延迟被 AI 推理管线主导（亚秒~数秒），SLE 的 ~12.5ms 占比 <1–2% —— 也就是说，即使 SLE 链路再快 10 倍，用户也几乎感知不到。**当前系统瓶颈不在通信，SLE 的低延迟优势在系统层面「被淹没」了。**

一句话：**SLE 确实用上了、参数也偏低延迟、相对 BLE 有可量化的约 5× 优势；但它既没被推到规格极限，也因为 AI 管线太慢而无法在端到端层面凸显出来。**

### 3.5 如何进一步凸显星闪优势（可操作 + 可量化）

要让「星闪优势」从「推导」变成「实测亮点」，建议：

1. **直接测空口延迟**：服务端发 Notify 前翻转一个 GPIO，客户端 `notification_cb` 里翻转另一个 GPIO，用双通道示波器/逻辑分析仪同时抓 —— 直接读出空口延迟（µs 级精度）。
2. **压低连接间隔再测**：把 `conn_interval` 从 0x32/0x64 调到 0x08（1ms）甚至更低，重测延迟，验证能否逼近亚毫秒。
3. **SLE vs BLE 同条件对比**：用 `MANUAL_SLE_SWITCH` 切到 BLE 路径，相同 1 字节载荷、相同测量方法，做一张 SLE/BLE 延迟对比表。
4. **抗干扰对比**：在 2.4GHz 强干扰（Wi-Fi 灌包/微波炉）下，各发 N=1000 次告警，统计送达率，体现 SLE 的抗干扰可靠性。
5. **缩短 AI 管线**：把推理改异步、喂样率补到 200Hz、必要时减小滑窗步长 —— 端到端延迟降下来后，SLE 的低延迟才会在系统层面「显形」。
6. **把测得的数字写进文档**：用实测表格替换本文 3.3 的「推导」标记，让优势可信。

> 上述每一项的**具体操作步骤、代码片段、接线方式、读数方法**，见配套实操手册《[性能测试与 SLE 延迟验证方法](性能测试与SLE延迟验证方法.md)》——照着做就能把本文标〔未实测〕〔推导〕的数字测出来。

## 5. 总体结论

- **实时性**：软实时系统。端到端延迟由 AI 推理管线（推理 + 640ms 滑窗节拍 + 2 窗确认）主导，量级亚秒~数秒；唯一未实测项是单次推理耗时。喂样率 100Hz 与模型 200Hz 存在 2× 偏差。
- **可靠性**：误报抑制有「概率门限 + 物理门控 + 多点命中 + 2 窗确认」四层防线，加 10s 冷却；内存全静态分配，系统稳定性基础好；SLE 链路有断连自愈和 ACK 闭环。主要薄弱点是「断连瞬间跌倒会丢失且被静默冷却」。
- **星闪优势**：已用上 SLE 并把参数配在偏低延迟档位，相对仓库 BLE 示例配置有可量化的约 **5×** 延迟优势；但未推到规格极限、未做实测对比，且因 AI 管线主导端到端延迟，SLE 的优势在系统层面尚未凸显。第 3.5 节给出了把它「测出来、显出来」的具体路径。
