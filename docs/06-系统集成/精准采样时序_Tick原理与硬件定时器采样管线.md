# 精准采样时序：Tick 原理与硬件定时器采样管线

> 主题：跌倒检测要求 IMU 以**严格 200Hz（5ms 间隔）**采样。最初用 `osDelay`
> 控制采样节拍，因 tick 时基的原理性限制根本做不到，后改为**硬件定时器
> 驱动的采样管线**。本文讲清这件事的前因后果与原理。
>
> 配套阅读：[`docs/04-TinyML模型/EdgeImpulse_模型集成与B+NN混合判定_2026-05-18.md`](../04-TinyML模型/EdgeImpulse_模型集成与B+NN混合判定_2026-05-18.md)

---

## 0. 一句话总览

`osDelay` 的参数单位是 **tick 不是毫秒**，而 WS63 的 1 tick = 10ms。用它做
采样节拍有三重硬伤：单位被误解、分辨率不够、周期会漂移。跌倒模型按严格
200Hz 训练，采样时间轴一旦失真，等于喂给模型错误的数据。最终改用**独立于
OS tick 的硬件定时器** + **中断只发信号量** + **采样/推理双任务 + 队列缓冲**
的管线，才拿到间隔恒定的 5ms 节拍。

---

## 1. 前因：用 osDelay 做采样节拍，错在哪

### 1.1 什么是 tick

**tick（系统节拍）是 RTOS 的「心跳」**：内核里有一个周期性的定时中断，每跳
一次叫一个 tick。内核所有「按时间」的服务 —— 任务延时、超时等待、时间片轮转
—— 都以 tick 为最小时间颗粒来计数。

tick 的频率由编译期配置项 `LOSCFG_BASE_CORE_TICK_PER_SECOND` 决定。

### 1.2 WS63 的 tick = 10ms

本工程 LiteOS 配置（`kernel/.../tools/build/config/ws63.config`，编译日志亦可见
`LOSCFG_BASE_CORE_TICK_PER_SECOND is set to 100`）：

```
LOSCFG_BASE_CORE_TICK_PER_SECOND = 100
```

即每秒 100 个 tick → **1 tick = 1/100 s = 10ms**。这是整个问题的根。

### 1.3 osDelay 的参数是 tick，不是毫秒

工程用的是 CMSIS-RTOS2 接口（LiteOS 上的 CMSIS 适配层）。`osDelay` 的原型：

```c
osStatus_t osDelay(uint32_t ticks);   // 参数名就是 ticks
```

**参数单位是「内核 tick 数」，不是毫秒。** 换算到本工程：

```
osDelay(1)   = 1  tick  = 10ms
osDelay(10)  = 10 ticks = 100ms      ← 注意！不是 10ms
osDelay(100) = 100 ticks = 1000ms
```

### 1.4 三个后果

把 `osDelay` 当成「毫秒延时」来写采样循环，会同时踩三个坑：

**后果一 —— 单位误解，频率差 10 倍**

代码里写 `osDelay(10)`，本意「10ms 一个样本 = 100Hz」，实际是 100ms 一个样本
= **10Hz**。频率直接差了一个数量级，却不会有任何编译报错或运行报错，极隐蔽。

**后果二 —— 分辨率根本不够**

tick = 10ms 是这个时基能表达的**最小非零延时**。要 200Hz 就要 5ms 周期 ——
**5ms 比 1 个 tick 还短，用 tick 延时根本无法表达**。`osDelay` 能做到的最快
周期就是 `osDelay(1)` = 10ms = 100Hz，离 200Hz 差一半，且毫无余量。

**后果三 —— 周期会累积漂移、还有抖动**

`osDelay` 是**相对延时**：它从「调用那一刻」起睡 N 个 tick。一个

```
while (1) { read_imu(); osDelay(1); }
```

的真实周期是 `读IMU耗时 + 延时`，读 IMU 的耗时被算进了周期里，每轮都在变 →
**周期不恒定、整体往后漂**。再加上 `osDelay` 的唤醒对齐到 tick 边界，本身就有
± 1 个 tick 的抖动。对「要求等间隔时间序列」的场景，这是致命的。

---

## 2. 为什么 200Hz 必须精准 —— 这是 ML 模型的硬要求

跌倒检测模型在 Edge Impulse 上按固定采样率训练，部署参数（`model_metadata.h`）：

```
EI_CLASSIFIER_FREQUENCY   = 200      // 200 Hz
EI_CLASSIFIER_INTERVAL_MS = 5        // 样本间隔 5 ms
```

模型学到的是「**相邻样本间隔恒为 5ms** 的时间序列」的形状特征 —— 自由落体多久、
冲击多陡、冲击后多久静止，全都是时间相关量。

如果实际采样是 10Hz、或时快时慢：

- 同一个真实动作在时间轴上被拉伸/压缩 → 卷积网络看到的波形形状变了；
- 等价于「**训练时的时间轴和部署时的时间轴对不上**」，和「量纲不一致」一样，
  会让模型输出失去意义。

所以**精准 200Hz 采样不是性能优化，是模型正确性的前提条件**。osDelay 方案
连这个前提都满足不了，必须换掉。

---

## 3. 解决方案：硬件定时器驱动的采样管线

### 3.1 总体结构

```
 硬件定时器(timer1, 5000µs)
        │  每 5ms 触发一次中断
        ▼
 sample_timer_cb()  ── 中断上下文 ── 只做一件事：释放节拍信号量
        │
        ▼  (信号量)
 采样任务 Sample_Task_Body  ── 高优先级(AboveNormal) ──
        │  1) 立即重载定时器   2) 读 MPU6050(I2C)   3) 样本入队列
        ▼  (消息队列, 深度128)
 推理任务 Fall_Detect_Task_Body  ── 普通优先级(Normal) ──
           出队 → 路径B状态机 → (触发时)NN推理 → 报警
```

关键思想：**把「精确计时」「采集」「推理」三件事彻底拆开**，各由最合适的
机制承担。

- 精确计时 → 交给**硬件定时器**（独立于 OS tick 的硬件计数器）；
- 采集（含阻塞 I2C）→ 交给一个**高优先级任务**；
- 推理（耗时上百 ms）→ 交给一个**普通优先级任务**；
- 中间用**信号量**做节拍传递、**消息队列**做数据缓冲。

### 3.2 硬件定时器为什么能做到 osDelay 做不到的事

WS63 的 `uapi_timer_*` 是**硬件外设定时器**，时基来自硬件计数器（µs 级），
**与 OS 的 10ms tick 完全无关**：

```c
uapi_timer_create(SAMPLE_TIMER_INDEX, &g_sample_timer);
uapi_timer_start(g_sample_timer, 5000 /*µs*/, sample_timer_cb, 0);
```

- 周期参数单位是**微秒**，5000µs 就是 5ms，分辨率绰绰有余；
- 计时由硬件完成，**不受任务调度、不受 CPU 当前在忙什么影响**，5ms 就是 5ms。

这是它和 `osDelay` 的本质区别：`osDelay` 是「软件按 tick 计数的相对睡眠」，
硬件定时器是「硬件按真实时间走的绝对节拍」。

### 3.3 为什么中断里只发信号量，不读 IMU

定时器中断回调 `sample_timer_cb()` 运行在**中断上下文**，里面**只**做一件事：

```c
static void sample_timer_cb(uintptr_t data) {
    osSemaphoreRelease(g_tick_sem);   // 仅释放节拍信号量
}
```

**不在中断里读 MPU6050**，因为：

- `uapi_i2c_master_read` 是**阻塞调用**，一次 I2C 事务要几百 µs；
- 中断上下文里**不允许阻塞 / 睡眠**，且长时间占用中断会拖垮整个系统的中断
  响应。

中断该做的是「**通知**」，不是「**干活**」—— 把「到点了」这个事件用信号量
抛给任务，真正的采集放到任务里做。这是 ISR 设计的通用原则：**中断里做最少
的事**。

### 3.4 为什么定时器重载放在任务里，不放在中断里

硬件定时器是**单次（one-shot）**的，触发后需要重新 `uapi_timer_start` 才会
有下一次。重载**没有放在中断回调里**，而是放在采样任务被唤醒后的第一步：

```c
osSemaphoreAcquire(g_tick_sem, osWaitForever);
uapi_timer_start(g_sample_timer, 5000, sample_timer_cb, 0);  // 任务里重载
MPU6050_Read_Accel_Gyro(...);                                 // 再读 IMU
```

原因：在中断上下文里重入 `uapi_timer_start`，会走进定时器驱动的
`in_timer_irq` 分支；当 timer1 还被其它软定时器共用时，这条路径存在
cycle（计数）下溢的风险。把重载改到任务上下文执行可规避。

并且**重载放在「读 IMU 之前」**：尽早重载，让下一个 5ms 窗口在「变长的
读 IMU 工作」之前就开始计时，把周期误差压到最小。

### 3.5 为什么用计数信号量

节拍信号量用的是**计数信号量**（`osSemaphoreNew(8, 0, NULL)`，最大计数 8）：

- 若采样任务偶尔被更高优先级的事打断、晚了一两拍，定时器中断照常触发、
  `osSemaphoreRelease` 把计数累加上去，**节拍不会丢**；
- 任务恢复后连续 `Acquire` 把欠下的拍补上。

如果用二值信号量，迟到期间的节拍就被合并丢失了。

### 3.6 为什么采样和推理拆成两个任务

| 任务 | 优先级 | 职责 | 耗时特性 |
|------|--------|------|----------|
| 采样任务 | AboveNormal（高） | 读 IMU、入队 | 每拍几百 µs，短而固定 |
| 推理任务 | Normal（普通） | 路径B + NN 推理 | NN 一次上百 ms，长而不定 |

**核心矛盾**：NN 一次 `run_classifier` 要上百毫秒，而采样节拍是 5ms。如果
放在同一个任务里，推理那上百毫秒内根本没法采样 → 直接丢几十个样本。

**拆开 + 优先级差**解决了它：

- 采样任务优先级更高 → 推理任务再忙，5ms 一到，采样任务**抢占**它、先把
  这一拍采了；
- 推理期间堆积的样本进**消息队列**（深度 128 = 128 × 5ms = **640ms 缓冲**）；
- 推理结束后推理任务再快速排空队列。只要单次推理 < 640ms，就**一个样本都
  不丢**（运行日志里 `drops` 恒为 0）。

## 4. 端到端时延预算

「时延」分几个层次，分别看：

### 4.1 采样时序精度（µs 级）

- 硬件定时器周期误差：硬件计数，5000µs 基本无误差；
- 中断→任务唤醒延迟：采样任务是高优先级，唤醒只需一次任务切换，约几 µs ~
  几十 µs；
- 任务里「先重载定时器」再读 IMU，把这点唤醒延迟排除在周期之外。

→ 采样间隔抖动远小于 1ms，相对 5ms 周期可忽略，模型拿到的是干净的等间隔序列。

### 4.2 缓冲时延（队列）

- 正常情况下队列几乎是空的（`q=0/128`），出队即处理，缓冲时延 ≈ 0；
- 仅在 NN 推理那上百 ms 内，队列短暂堆积约 20~30 个样本，推理结束即排空。
  这是**用一点缓冲时延换「不丢样」**，是有意的设计取舍。

### 4.3 检测时延（算法固有）

路径 B 必须观察「冲击后静止」整整 `STILL_WINDOW = 240` 个样本（240 × 5ms =
**1.2s**）才能确认跌倒。所以**从落地到确认，固有约 1.2s 延迟** —— 这是「要
确认人确实躺地不动」这件事本身的代价，不是缺陷。

### 4.4 跌倒 → 报警总时延（估算）

```
冲击落地
  └─ 路径B确认           ≈ 1.2 s   (冲击后静止观察窗)
       └─ NN 复核        ≈ 0.1~0.3 s (run_classifier)
            └─ 星闪/BLE 发送 ≈ 数十 ms
合计                     ≈ 1.5 s 左右
```

对跌倒检测，人已在地上，1.5s 量级的报警时延完全可接受 —— 这里**优先保证
判断正确（不误报、不漏报），不是抢这一两秒**。

## 5. 原理小结与经验

1. **认清时基单位**：RTOS 的 `osDelay` 类延时，参数单位是 **tick**，tick 多长
   由 `LOSCFG_BASE_CORE_TICK_PER_SECOND` 决定。本工程 1 tick = 10ms，
   `osDelay(10)` 是 100ms 不是 10ms。用之前先确认。

2. **tick 时基天生不适合高频精确节拍**：它的分辨率就是一个 tick（这里 10ms），
   且是相对延时、会累积漂移。要 5ms 级、间隔恒定的节拍，必须上**硬件定时器**。

3. **采样时序是 ML 的正确性前提**：模型按固定采样率训练，部署端采样率/间隔
   不一致 = 时间轴失真 = 喂错数据，和量纲不一致同等严重。

4. **中断里只做最少的事**：阻塞操作（I2C 读）绝不能进中断；中断负责「通知」，
   用信号量把事件抛给任务，干活放任务里。

5. **生产者-消费者解耦**：把「固定快节拍的采集」和「耗时不定的处理」用
   「高优先级任务 + 队列 + 低优先级任务」拆开，是嵌入式实时系统的通用范式。
   队列深度按「最坏处理耗时 ÷ 采样周期」留足。

6. **用计数信号量传节拍**：偶发迟到时节拍可累积、不丢拍。
