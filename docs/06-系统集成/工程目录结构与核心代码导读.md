## 3. 构建系统的"角色裁剪"逻辑（**记住这个表格**）

`fall_detect/src/CMakeLists.txt` 读 `menuconfig` 写入的 `ws63_liteos_app.config`，
按 `CONFIG_FALL_DETECT_ROLE_*` 决定本次到底编哪些文件：

| Kconfig 选项 | 编入的关键源 | 删除的关键源 | 拉入的官方底层 |
|--------------|--------------|--------------|----------------|
| `FALL_DETECT_ROLE_SERVER=y` + `FALL_DETECT_USE_SLE=y`（板 A 当前用法）| `sle_server_task.c` + 官方 `sle_speed_server_adv.c` | `sle_client_task.c`, `ble_server_task.c`, 官方 `sle_speed_server.c` | `bt/sle/sle_speed_server/inc/` |
| `FALL_DETECT_ROLE_CLIENT=y` + `FALL_DETECT_USE_SLE=y`（板 B 当前用法）| `sle_client_task.c` | `sle_server_task.c`, `ble_server_task.c` | `bt/sle/sle_speed_client/inc/` |
| `FALL_DETECT_USE_SLE=n`（BLE 回退）| `ble_server_task.c` + 官方 `ble_speed_server.c/adv.c` | `sle_server_task.c` | `bt/ble/ble_speed_server/inc/` |

**为什么不能编 `sle_speed_server.c`？** 那份官方文件里写死了自己的连接回调和 `app_run` 入口，
启动期会把 `sle_conn_register_cbks()` 又覆盖回它自己的回调，导致我们的 `g_sle_conn_hdl`
永远停在 `0xFFFF` —— 发通知一律打印 `No client connected`。所以**只编广播部分** `sle_speed_server_adv.c`。

**为什么 EI SDK 排掉这一堆 `porting/*/`？** WS63 RISC-V toolchain 会定义 `__unix__`，
EI 的 `porting/posix/*.cpp` 不带 `weak` 属性的 `ei_read_timer_ms/us`，
和我们 `ei_porting_ws63.cpp` 里的同名实现起符号冲突 —— 整批 `arduino/android/posix/...` 一律删掉。

C++ 这边补三件事：
- `-std=c++14`（默认 `gnu99` 不能编 EI 那一摞 cpp）
- 删 `-Werror`（EI 生成代码触发 `-Wnarrowing` 等）
- `-fno-exceptions -fno-rtti`（不依赖 `libgcc_eh`，否则链接报错）
- 加 `-DEI_CLASSIFIER_ALLOCATION_STATIC=1`（强制走静态内存池，杜绝 -22）

## 4. 核心代码导读（按数据流顺序）

> 下面只挑"删掉就跑不通 / 改错就误报"的关键函数与代码段。完整算法/调参在
> `跌倒判定算法_完整逻辑与调参复盘.md`、采样原理在 `精准采样时序_Tick原理与硬件定时器采样管线.md`。

### 4.1 `main_task.c` — 跌倒任务主循环

**采样管线**（`main_task.c:53-142`）：
- 硬件 `timer1` 5ms 一跳，中断只 `release(信号量)` —— 不在中断里读 I2C（阻塞），不在中断里 `uapi_timer_start`（驱动 in_timer_irq 分支有 cycle 下溢风险）。
- `Sample_Task_Body`（优先级 `osPriorityAboveNormal`）从信号量醒来 → 重载 timer → 读 IMU → 入 `osMessageQueue`（深度 128）。
- 队列满就丢并计数 `g_drop_count`，**绝不阻塞采样节拍**。
- `osDelay` 分辨率 10ms 还抖，根本喂不到 200Hz NN 的恒定间隔，所以才用硬件 timer。

**B+NN 混合判定主循环**（`main_task.c:211-291`）：

```c
// 每个样本：先喂 NN 环形缓冲、再跑 B 路状态机
EI_Fall_Push(...);
int status = Fall_Algo_Process(...);

if (status == 1) {                 // B 路确认
    ei_fall_result_t nn = EI_Fall_Classify();
    if (nn.valid && nn.normal_percent >= NN_VETO_NORMAL_PCT /*=95*/) {
        // NN 高置信判 normal → 否决，不报警不进冷却
    } else {
        // NN 同意 / 不可用 / 置信度不足 → 报警
        sle_send_fall_alert(...);  // 或 BLE
        g_ws2812b_alert_active = true;
        fall_cooldown_start = now_ms;
    }
}
```

**关键设计**：NN 是"复核否决器"，不是"主触发器"。这样即使 NN 误判 `normal=95%`，
也只能否决一次本就要报的；真摔 NN 测得 `normal` 远低于 95，永远不会被误杀。
**保守优先不漏报。**

**MPU6050 不在线时不进 200Hz 采样**（`main_task.c:166-172`）：
若不挡住，高优先级采样任务会忙等阻塞 I2C → 100% CPU → 饿死喂狗任务 → 看门狗 NMI 复位循环。
这是早期实测踩过的坑。

**数据采集模式 `FALL_LOG_MODE`**（`main_task.c:181-201`）：取消注释重编后，固件改为
串口逐样本输出 6 轴 CSV（`ax*1000, gy*100, ...`），不做检测 —— 配合
`ws63-edge-ai-guide/tools/capture_imu.py` 直接采训练数据。**采完务必注释回去**。

### 4.2 `fall_algo.c` — 路径 B 状态机（不依赖任何模型）

四段序列：

```
IDLE  →[acc<0.75G]→  FREEFALL  →[acc>2.20G in 1s]→  POST_IMPACT
                       ↑                                      ↓
                       └─ 失重<70ms 或 >750ms 视为非跌倒 ─┐    │
                                                          ↓    ↓
                                                     四项齐全？
                                                  ┌─────────────┐
                                                  │ 冲击 ≥4.0G  │
                                                  │ 静止占比≥50%│
                                                  │ 倾角 ≥45°   │
                                                  └────┬────────┘
                                                       ↓
                                                   return 1
```

**倾角判据**（`fall_algo.c:92-110`）：跑 IDLE 时低通累计"直立重力方向" `s_gref_*`；
冲击后静止段累计"事件后重力方向" `s_gpost_*`；夹角 < 45° 判为原地起跳（躯干仍直立），否决。
**这条挡掉了"起跳-落地"这种实测会撞穿冲击门限的假阳性。**

**`IMPACT_HARD_G=4.0`** 是核心调参点（`fall_algo.c:43`）：实测快速蹲下/坐下冲击 ≤3.1G，
真跌倒 ≥5.3G，4.0 落在两者中间。每次事件都会打印 `impact=x.xxG` 供再调。

### 4.3 `mpu6050.c` — IMU 驱动 + 两套自救

**I2C 总线恢复**（`mpu6050.c:77-117`）：CPU 复位（看门狗/烧录/掉电）打断 I2C 读时，
从机可能停在半字节、持续把 SDA 拉低 → 总线锁死且**跨 CPU 复位保留**。
解法：把 SCL/SDA 当 GPIO，给 ≤9 个时钟脉冲让从机移完卡住的字节、释放 SDA，再补一个 STOP。

**传感器自复位救援**（`mpu6050.c:220-233`）：工作中 |acc| 恒 ≈1G。若连续 200 样本 (1s)
|acc|≈0，说明 MPU6050 被冲击/电压跌落复位回睡眠态；CPU 没复位，所以
**自动重写唤醒+配置寄存器**把它救回来。

**WHO_AM_I 探活**（`mpu6050.c:147-157`）：上电首次 I2C 偶发失败，重试 5 次都读不到才返回 false。
不只看一次写是否 ACK，避免把"偶发首写失败"误判成"传感器缺失"，触发上层把采样关掉。

### 4.4 `ei_fall.cpp` — NN 复核器（2 通道朝向无关特征）

**为何用 |acc|/|gyro| 而非 6 轴原始值**：旧 6 轴模型 EI 测 97%、板上真摔 fall=0%，
根因是"朝向捷径"——录 fall/normal 时传感器朝向不一致，模型靠朝向区分而非物理。
改用 `sqrtf(ax²+ay²+az²)` `sqrtf(gx²+gy²+gz²)` 两路幅值后，
模型与佩戴朝向完全无关（与路径 B 同理）。

**EI 里 DSP 块用 Flatten 而非 Raw**：Raw + 逐位置 StandardScaler 让模型对
"冲击峰值在样本第几位"敏感 —— 训练数据冲击固定在 240、板上部署窗口冲击常在 300，
导致 EI 测 95%、板上真摔 fall=10%。改 Flatten（位置无关统计量，NN 输入 14 维）后
板上真摔输出 100%。

**环形缓冲 + 时间有序展开**（`ei_fall.cpp:40-46, 99-110`）：
600 样本 = 3 秒 × 200Hz 始终持有最近 3s；触发后两段 memcpy 拼成连续窗口送 `run_classifier`。
`run_classifier` 一次上百 ms，因为采样任务优先级更高所以队列不会溢。

**`#pragma GCC diagnostic ignored "-Wnarrowing"`**（`ei_fall.cpp:26-31`）：EI 生成的
`model_variables.h` 里个别大整数标量未写成浮点字面量，在 `const float[]` 初始化里
被 GCC 判 narrowing，被 `-Werror` 升级成错误 —— 局部包住三个 include 就解决。

### 4.5 `ei_porting_ws63.cpp` — EI SDK 移植层

EI SDK 把 `ei_printf / ei_malloc / ei_read_timer_*` 声明为"用户必须实现"。
自带的各平台实现都被 `#if EI_PORTING_<TARGET>` 包起来，WS63 不匹配任何一个 → 必须自己实现。

**静态内存池 64KB**（`ei_porting_ws63.cpp:30`）：`run_classifier` 会通过 `ei_malloc` 申请
DSP 中间矩阵（≈14KB）+ 若干小块。改走 `LOS_MemInit` 后的静态池而不是系统堆，
一次性框定 NN 的 RAM 占用，不与系统其它分配相互挤占（消除早期 -22 分配失败）。

### 4.6 `sle_server_task.c` — 板 A SLE 服务端

**关键修复（注释里也写得很清楚）**：

| 处 | 老问题 | 修法 |
|----|--------|------|
| `property.value_len` (#165) | 漏填，初值读取行为未定义 | 显式设 `sizeof(property_value)` |
| `operate_indication` (#171) | 只有 READ\|NOTIFY，客户端写 ACK 协议栈直接拒，回调永不触发 | 加上 `BIT_WRITE` |
| 描述符类型 (#178-186) | 用 `CLIENT_CONFIGURATION` 时 CCCD 每次重连重置成 0x0000，通知静默丢包 | 改用 `USER_DESCRIPTION` |
| `sle_server_on_stack_ready` (#213-235) | 与 `sle_speed_server.h` 全局符号 `sle_enable_server_cbk(void)` 重名冲突 | 改名 + 留空实现的同名存根满足链接器 |
| 连接成功后主动握手 (#82-89) | 不发，依赖 client 写 descriptor 激活，跨重连不可靠 | 连上就发一字节 `0x01` 握手通知 |
| Write 回调按字节区分 (#107-120) | 老代码全部按"普通写"打印，看不到 ACK | `data[0]==0x06` → 打印 ACK 确认日志 |

对外只暴露一个接口：`errcode_t sle_send_fall_alert(uint8_t *data, uint16_t len)` ——
被 `main_task.c` 在确认跌倒时调用，未连接则丢弃返回错。

### 4.7 `sle_client_task.c` — 板 B SLE 客户端

数据流：`enable_sle` → `seek` 扫到 MAC `11:22:33:44:55:66`（板 A 写死的本地地址）→ 停扫 → `connect`
→ `pair` → `exchange MTU=512` → `find_structure` → 匹配到 service UUID `0xABCD`
→ 向 service handle 写一字节 `0x01` 激活通道。

**收到 `0x05` 即触发本地三联报警**（`my_sle_speed_notification_cb`, #102-122）：
1. `fall_alert_set(true, 0)` —— 蜂鸣器低电平拉响 + 普通 LED + WS2812B 红色 5Hz 持续闪
2. `fall_alert_gateway_post_fall(0x05)` —— 唤醒 Wi-Fi gateway 任务，HTTP POST 到云
3. `fall_alert_4g_dtu_post_fall(0x05)` —— 唤醒 4G DTU 任务，UART 让 V100C 拨电话+发短信
4. 写一字节 `0x06` ACK 回服务端（构成完整闭环）

**强制启动延时**（#252-258）：`enable_sle` 后 `osal_msleep(1000)` 再 `sle_start_seek`，
错峰启动射频，避开 Flash 挂载/雷达参数读取的供电瞬态尖峰。

**`seek_param.seek_phys = 1`**（#244）：不设这一行扫描器物理层是瞎的，看不到任何广播。

**报警守护任务**（#68-82）：50ms tick 检查 `g_alert_deadline_ms`，到期主动关蜂鸣器 —— 防止
单次跌倒后蜂鸣器永远响。`hold_ms=0` 表示"持续响到收到 stop 才停"。

### 4.8 `fall_alert_gateway.c` — 板 B Wi-Fi 上云

状态机 `INIT → SCANNING → SCAN_DONE → FOUND_TARGET → CONNECTING → CONNECT_DONE → GET_IP → READY`，
带连接断开后回到 INIT 重连。

`fall_alert_gateway_post_fall(0x05)` 把事件标记 pending，主任务 200ms 轮询，
拼一个简单 HTTP POST JSON 发到 `FALL_GATEWAY_SERVER_HOST:8080/api/fall-alert`。
`FALL_GATEWAY_CLOUD_COOLDOWN_MS = 60s` 防一次跌倒重复打云端。

### 4.9 `fall_alert_4g_dtu.c` — 板 B 4G 拨号/短信

UART1 (GPIO15/16) → V100C / Air780EHV 4G 模块。V100C 跑 LuatOS，
我们的 `dtu_task_fall_alert.lua` 已经烧到 V100C 里：监听 `UartGetRecChAndDel(2)`，
收到 WS63 推的 JSON 就 `cc.dial(phone)` 拨号 + `sms.send(phone, text)` 发短信。

两个开关：`FALL_ALERT_4G_DTU_CALL_ENABLED` / `FALL_ALERT_4G_DTU_SMS_ENABLED` 可独立关掉。

### 4.10 `ws2812b.c` — RISC-V cycle 精确位时序灯带驱动

旧实现用 `nop` 计数循环模拟延时，注释按 -O0 调，函数实为 -O2 → 脉宽只有规格一半，
灯带后段颜色乱、灯珠不亮。新实现读 `csrr cycle` 的 RISC-V 周期计数器忙等，
周期数由 `ws2812b_init()` 用 TCXO 标定 CPU 主频后换算 —— 跨编译档位都稳。

`g_ws2812b_alert_active` 是全局 volatile flag，置 true 后专门的 flash 任务下一个 tick
就以 5Hz 红色闪；置 false 后自动重绘绿色待机（不黑屏）。
