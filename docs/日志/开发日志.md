## 2026.03.27 — C++在海思SDK中的编译问题

**问题**：在海思SDK编译环境中运行C++代码时，链接阶段报错。

**根本原因**：C++编译链依赖Linux平台的libc，而LiteOS是极小的轻量级平台，不提供这些依赖。

**解决思路**：禁用C++异常（`-fno-exceptions`）、RTTI（`-fno-rtti`），并提供缺失的运行时符号。

## 2026.04.15 — 理解推理窗口机制

## 2026.04.26 — SLE 星闪通知机制调试全记录

**目标**：实现跌倒检测服务端（板A）检测到跌倒时，向星闪客户端（板B）推送通知，客户端打印 `FALL` 并点亮 LED。

### 问题1：客户端 `notification_cb` 永远不触发

**现象**：服务端 `ssaps_notify_indicate` 返回 SUCCESS，日志显示 `[SLE Server] Fall alert sent successfully!`，但客户端完全无反应，只打印心跳 `[CLIENT] 1`。

**调试过程**：
1. 首先怀疑 SLE 连接问题 → 客户端心跳正常，连接本身无误。
2. 对比官方 `sle_speed_client` 示例发现：官方在 MTU 协商完成后立即调用 `ssapc_find_structure` 进行服务发现，我们的代码跳过了这一步。

**根本原因**：WS63 SLE SSAP 协议栈要求客户端完成服务发现（`ssapc_find_structure`），才会将服务端的 Notify 包路由到应用层的 `notification_cb`。缺少这一步，通知在协议栈内部被静默丢弃。

**修复**：在 MTU 协商回调 `my_sle_exchange_info_cbk` 中补充调用服务发现：

```c
ssapc_find_structure_param_t find_param = {0};
find_param.type     = SSAP_FIND_TYPE_PRIMARY_SERVICE;
find_param.start_hdl = 1;
find_param.end_hdl  = 0xFFFF;
ssapc_find_structure(client_id, conn_id, &find_param);
```

**结果**：服务发现成功（`start_hdl=0x10 end_hdl=0x11`），但通知仍未收到，问题未彻底解决。

---

### 问题2：服务发现成功后仍收不到通知

**现象**：客户端日志打印了 `Service discovery complete`，但跌倒后依然没有 `FALL` 输出。

**根本原因**：SLE SSAP 与 BLE 一样存在 **CCCD（Client Configuration Descriptor，客户端配置描述符）** 机制。服务端属性必须注册 `SSAP_DESCRIPTOR_CLIENT_CONFIGURATION` 描述符，协议栈才会为每条连接维护"通知订阅状态"。我们的服务端缺少这一步，导致 `ssaps_notify_indicate` 虽然返回成功，但数据在协议栈层面被丢弃。

**对比官方示例**（`sle_speed_server.c`）发现：官方在 `ssaps_add_property_sync` 之后还额外调用了 `ssaps_add_descriptor_sync`，我们的代码完全缺少这一步。

**双重修复方案**：

**① 服务端**（`sle_server_task.c`）：在 property 注册后、启动服务前添加 CCCD 描述符，初始值 `0x01` 表示默认开启通知：

```c
ssaps_desc_info_t descriptor = {0};
static uint8_t cccd_val[2] = {0x01, 0x00};
descriptor.permissions        = SSAP_PERMISSION_READ | SSAP_PERMISSION_WRITE;
descriptor.operate_indication = SSAP_OPERATE_INDICATION_BIT_READ | SSAP_OPERATE_INDICATION_BIT_WRITE;
descriptor.type               = SSAP_DESCRIPTOR_CLIENT_CONFIGURATION;  // 0x02
descriptor.value              = cccd_val;
descriptor.value_len          = 2;
ssaps_add_descriptor_sync(server_id, service_handle, property_handle, &descriptor);
```

**② 客户端**（`sle_client_task.c`）：服务发现完成后向服务端写一次激活字节，激活通知路由通道（与官方 `sle_speed_client` 示例行为一致）：

```c
// find_structure_cmp_cbk 中
static uint8_t s_activate = 0x01;
ssapc_write_param_t wr = {0};
wr.handle   = g_found_service_start_hdl;
wr.type     = SSAP_PROPERTY_TYPE_VALUE;
wr.data_len = 1;
wr.data     = &s_activate;
ssapc_write_req(client_id, conn_id, &wr);
```

---

### 问题3：客户端收到通知有明显延迟

**现象**：跌倒后客户端不会立即打印 `FALL`，存在数秒延迟。

**根本原因**：延迟不在 SLE 通信侧（<100ms），而完全来自 AI 推理管道：

| 阶段 | 耗时 |
|------|------|
| DSP 特征提取（Edge Impulse） | ~3045 ms |
| TFLite 神经网络推理 | ~2798 ms |
| **单次推理合计** | **~5.8 秒** |

推理在主线程同步执行，期间传感器完全停止采样。最坏情况下（跌倒发生在上一轮推理刚开始时），延迟可达 **~12 秒**。

**决策**：维持现有 AI 方案，TinyML 端侧推理是本项目核心亮点。当前延迟属于 RISC-V 无硬件 DSP 加速的性能特性，后续可通过将推理移至独立线程改善采样连续性，或在 Edge Impulse 平台重训更小窗口的模型降低推理时间。

---

### 最终通信链路（修复后）

```
[板A - Server]                              [板B - Client]
  MPU6050 100Hz 采样
      ↓ 每 30 个样本触发
  Edge Impulse TFLite 推理 (~5.8s)
      ↓ 跌倒概率 > 80%
  ssaps_notify_indicate(data=0x05)
      ─────── SLE SSAP Notify ──────────→   notification_cb 触发
                                               GPIO_09 LED 点亮
                                               串口打印 "FALL"
                                               ssapc_write_req(0x06) ACK 回传
      ←───── ssaps_write_request_cbk ──────  
  打印 "ACK received from client!"
```

## 2026.04.30 — 中文注释乱码修复 + 编码规范落地

**问题现象**：`main_task.c`、`sle_client_task.c`、`ws2812b.c/.h` 中中文注释显示为 `鏄...`、`涓...`、`�?` 等乱码，阅读和维护成本很高。

**根本原因**：
1. 历史文件发生过“UTF-8 按 GBK 解码后再次保存”的链式编码错误（典型 Mojibake）。
2. 部分注释尾部包含不可逆损坏字符（`�`），说明原始字节信息已经丢失，无法 100% 自动还原。

**本次修复策略**：
- 先按 GBK→UTF-8 方向做批量回转，恢复大部分中文注释可读性；
- 对不可逆字符统一替换为 `?`，避免继续传播乱码；
- 将相关文件统一保存为 **UTF-8（无BOM）**，并将该规则纳入项目工程规范。

**涉及代码文件**（设计与实现相关）：
- `application/samples/my_demo/fall_detect/src/main_task.c`
- `application/samples/my_demo/fall_detect/src/sle_client_task.c`
- `application/samples/my_demo/fall_detect/src/ws2812b.c`
- `application/samples/my_demo/fall_detect/inc/ws2812b.h`

**修复脚本示例**（PowerShell）：

```powershell
$files = @(
  'application\samples\my_demo\fall_detect\inc\ws2812b.h',
  'application\samples\my_demo\fall_detect\src\main_task.c',
  'application\samples\my_demo\fall_detect\src\ws2812b.c',
  'application\samples\my_demo\fall_detect\src\sle_client_task.c'
)
$gbk = [System.Text.Encoding]::GetEncoding(936)
$utf8NoBom = New-Object System.Text.UTF8Encoding($false)
foreach ($p in $files) {
  $text  = Get-Content $p -Raw -Encoding UTF8
  $fixed = [System.Text.Encoding]::UTF8.GetString($gbk.GetBytes($text))
  $fixed = $fixed -replace '�?','?' -replace '�','?'
  [System.IO.File]::WriteAllText((Resolve-Path $p), $fixed, $utf8NoBom)
}
```

**验证方式**：
- 使用 `rg` 检索常见乱码特征串（如 `鏄`、`涓`、`锟`、`�`）；
- 逐文件抽查关键注释段，确认主要逻辑注释恢复可读；
- 对残留 `?` 位置人工复核并按语义补全（后续持续清理）。

**本次新增技术栈/工程能力**：

| 层次 | 技术 / 工具 |
|------|------------|
| 文本编码治理 | UTF-8（无BOM）统一保存策略 |
| 编码修复工具 | PowerShell + .NET Encoding（GBK:936 / UTF-8） |
| 质量检查 | `rg` 乱码特征检索 + 人工语义复核 |

## 2026.05.01 — WS2812B 灯带告警功能集成与调试

**目标**：在跌倒检测触发后，灯带进入红色闪烁告警；平时保持熄灭，不影响主业务线程。

**遇到的问题**：
1. **颜色异常/全白/不亮**：WS2812B 对高低电平脉宽非常敏感，初始循环计数与板子主频不匹配。  
2. **告警不稳定**：在主线程里直接控制灯带，容易和采样/推理节奏互相干扰。  
3. **复位时序不充分**：发送帧前后低电平保持时间不足，导致偶发花屏或首帧丢失。  

**解决办法**：
- 在 `ws2812b.c` 中按 WS63 实测主频重新调参 `T1H_CNT/T0H_CNT`，并采用 `O0 + volatile` 循环确保延时不被优化。  
- 增加独立 `ws2812b_flash_task` 任务：  
  - `g_ws2812b_alert_active = false` 时空转；  
  - `true` 时执行“红灯 400ms / 熄灭 400ms”循环。  
- 在发送跌倒告警成功后，设置 `g_ws2812b_alert_active = true`，并使用 `WS2812B_ALERT_HOLD_MS` 自动超时关闭。  
- 在初始化阶段增加上电稳定与复位低电平保持，避免上电初期随机色。  

**对应设计代码**：
- `application/samples/my_demo/fall_detect/src/ws2812b.c`（位级时序驱动、闪烁任务）
- `application/samples/my_demo/fall_detect/inc/ws2812b.h`（接口与时序调参说明）
- `application/samples/my_demo/fall_detect/src/main_task.c`（告警状态联动与自动关闭）
- `application/samples/my_demo/fall_detect/src/sle_client_task.c`（客户端告警联动）

**结果**：
- 跌倒触发后可稳定看到红色闪烁；  
- 空闲时灯带不误亮，主循环采样与通信链路保持稳定；  
- 告警可自动结束，避免长期占用视觉提示。

**本次新增技术栈**：

| 层次 | 技术 / API |
|------|-----------|
| 灯带驱动 | WS2812B 单总线位时序（bit-banging） |
| 引脚控制 | `uapi_gpio_set_dir`、`uapi_gpio_set_val` |
| 任务调度 | LiteOS `osThreadNew` + `osDelay` 周期闪烁 |
| 告警联动 | `g_ws2812b_alert_active` + `WS2812B_ALERT_HOLD_MS` |
| 系统协同 | AI推理结果与SLE/BLE告警同步触发灯效 |

## 2026.05.07 - Edge Impulse + SisFall 模型部署到 WS63 的完整调试

**目标**：将 SisFall 二分类模型部署到 WS63 + LiteOS 开发板，并在串口实时输出 `normal` / `FALL_RISK` 状态，通过 SLE 发送 SOS 告警。

**关键模型参数**：`256 samples`、`6 axes`、`200 Hz`、`5 ms interval`，输入轴为 `accX + accY + accZ + gyrX + gyrY + gyrZ`。

**主要问题与解决方案**：

1. **AI 没有运行**：固件处于 Client 模式，MPU6050 与 Edge Impulse 推理只在 Server 模式执行；已强制传感器板运行 Server 模式。
2. **`run_classifier()` 返回 `-22`**：Edge Impulse 生成的全局 C++ impulse handle 在 LiteOS 启动时没有可靠构造；改为运行时 placement-new 构造 `ei_impulse_handle_t`。
3. **推理时间字段异常**：EI SDK 计时函数未适配 WS63 平台，去掉 `dsp/infer` 耗时打印。
4. **模型输出极端化**：SisFall 数据与 MPU6050 实测数据存在尺度差异，特别是陀螺仪单位；对 gyro 使用 `dps / 250.0f` 归一化。
5. **静止时 `ai_fall` 仍可能很高**：确认是模型 domain mismatch，因此最终状态不直接采用 AI 分数，而加入物理门控。
6. **静止或轻微动作误触发 gate**：显式配置 MPU6050 的 DLPF、采样率、加速度量程和陀螺仪量程，并增加陀螺仪零偏校准。
7. **单个异常点影响滑动窗口**：加入 `hits` 机制，要求多个采样点满足冲击/失重/旋转条件；再加入连续窗口 `confirm=2/2` 后才报警。

**最终串口判断格式**：

```text
[AI] status=normal ai_fall=99% normal=1% gate=NO confirm=0/2 peak_acc=1.10G min_acc=1.09G peak_gyr=0.00 hits=0/0/0
[AI] status=FALL_RISK ai_fall=100% normal=0% gate=YES confirm=2/2 peak_acc=3.20G min_acc=0.24G peak_gyr=3.12 hits=7/2/28
```

**结论**：工程上已达到比赛演示可用状态。静止状态不报警，模拟跌倒/撞击/翻转可触发 `FALL_RISK`。但模型本身仍存在板端数据分布不匹配，后续产品级方案建议使用 WS63 + MPU6050 自采数据重新训练。
