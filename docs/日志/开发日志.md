## 2026.03.27 — C++在海思SDK中的编译问题

**问题**：在海思SDK编译环境中运行C++代码时，链接阶段报错。

**根本原因**：C++编译链依赖Linux平台的libc，而LiteOS是极小的轻量级平台，不提供这些依赖。

**解决思路**：禁用C++异常（`-fno-exceptions`）、RTTI（`-fno-rtti`），并提供缺失的运行时符号。

## 2026.04.15 — 理解推理窗口机制

**理解**：开发板启动后**不是立即开始推理**，而是先采集满 `100×3` 帧数据（填满buffer），之后用滑动窗口方式持续推理。

**新问题思考**：如果长时间未发生跌倒，数据会一直循环覆盖buffer，这是合理的。数据保存在RAM中的循环缓冲区，不需要持久化存储。

## 2026.04.26 — SLE 星闪通知机制调试全记录

**目标**：实现跌倒检测服务端（板A）检测到跌倒时，向星闪客户端（板B）推送通知，客户端打印 `FALL` 并点亮 LED。

### 问题1：客户端 `notification_cb` 永远不触发

**现象**：服务端 `ssaps_notify_indicate` 返回 SUCCESS，日志显示 `[SLE Server] Fall alert sent successfully!`，但客户端完全无反应，只打印心跳 `[CLIENT] 1`。

**调试过程**：
1. 首先怀疑 SLE 连接问题 → 客户端心跳正常，连接本身无误。
2. 对比官方 `sle_speed_client` 示例发现：官方在 MTU 协商完成后立即调用 `ssapc_find_structure` 进行服务发现，我们的代码跳过了这一步。

**根本原因**：WS63 SLE SSAP 协议栈要求客户端完成服务发现（`ssapc_find_structure`），才会将服务端的 Notify 包路由到应用层的 `notification_cb`。缺少这一步，通知在协议栈内部被静默丢弃。

**修复**：在 MTU 协商回调 `my_sle_exchange_info_cbk` 中补充调用服务发现：

```c
ssapc_find_structure_param_t find_param = {0};
find_param.type     = SSAP_FIND_TYPE_PRIMARY_SERVICE;
find_param.start_hdl = 1;
find_param.end_hdl  = 0xFFFF;
ssapc_find_structure(client_id, conn_id, &find_param);
```

**结果**：服务发现成功（`start_hdl=0x10 end_hdl=0x11`），但通知仍未收到，问题未彻底解决。

---

### 问题2：服务发现成功后仍收不到通知

**现象**：客户端日志打印了 `Service discovery complete`，但跌倒后依然没有 `FALL` 输出。

**根本原因**：SLE SSAP 与 BLE 一样存在 **CCCD（Client Configuration Descriptor，客户端配置描述符）** 机制。服务端属性必须注册 `SSAP_DESCRIPTOR_CLIENT_CONFIGURATION` 描述符，协议栈才会为每条连接维护"通知订阅状态"。我们的服务端缺少这一步，导致 `ssaps_notify_indicate` 虽然返回成功，但数据在协议栈层面被丢弃。

**对比官方示例**（`sle_speed_server.c`）发现：官方在 `ssaps_add_property_sync` 之后还额外调用了 `ssaps_add_descriptor_sync`，我们的代码完全缺少这一步。

**双重修复方案**：

**① 服务端**（`sle_server_task.c`）：在 property 注册后、启动服务前添加 CCCD 描述符，初始值 `0x01` 表示默认开启通知：

```c
ssaps_desc_info_t descriptor = {0};
static uint8_t cccd_val[2] = {0x01, 0x00};
descriptor.permissions        = SSAP_PERMISSION_READ | SSAP_PERMISSION_WRITE;
descriptor.operate_indication = SSAP_OPERATE_INDICATION_BIT_READ | SSAP_OPERATE_INDICATION_BIT_WRITE;
descriptor.type               = SSAP_DESCRIPTOR_CLIENT_CONFIGURATION;  // 0x02
descriptor.value              = cccd_val;
descriptor.value_len          = 2;
ssaps_add_descriptor_sync(server_id, service_handle, property_handle, &descriptor);
```

**② 客户端**（`sle_client_task.c`）：服务发现完成后向服务端写一次激活字节，激活通知路由通道（与官方 `sle_speed_client` 示例行为一致）：

```c
// find_structure_cmp_cbk 中
static uint8_t s_activate = 0x01;
ssapc_write_param_t wr = {0};
wr.handle   = g_found_service_start_hdl;
wr.type     = SSAP_PROPERTY_TYPE_VALUE;
wr.data_len = 1;
wr.data     = &s_activate;
ssapc_write_req(client_id, conn_id, &wr);
```

---

### 问题3：客户端收到通知有明显延迟

**现象**：跌倒后客户端不会立即打印 `FALL`，存在数秒延迟。

**根本原因**：延迟不在 SLE 通信侧（<100ms），而完全来自 AI 推理管道：

| 阶段 | 耗时 |
|------|------|
| DSP 特征提取（Edge Impulse） | ~3045 ms |
| TFLite 神经网络推理 | ~2798 ms |
| **单次推理合计** | **~5.8 秒** |

推理在主线程同步执行，期间传感器完全停止采样。最坏情况下（跌倒发生在上一轮推理刚开始时），延迟可达 **~12 秒**。

**决策**：维持现有 AI 方案，TinyML 端侧推理是本项目核心亮点。当前延迟属于 RISC-V 无硬件 DSP 加速的性能特性，后续可通过将推理移至独立线程改善采样连续性，或在 Edge Impulse 平台重训更小窗口的模型降低推理时间。

### 最终通信链路（修复后）

```
[板A - Server]                              [板B - Client]
  MPU6050 100Hz 采样
      ↓ 每 30 个样本触发
  Edge Impulse TFLite 推理 (~5.8s)
      ↓ 跌倒概率 > 80%
  ssaps_notify_indicate(data=0x05)
      ─────── SLE SSAP Notify ──────────→   notification_cb 触发
                                               GPIO_09 LED 点亮
                                               串口打印 "FALL"
                                               ssapc_write_req(0x06) ACK 回传
      ←───── ssaps_write_request_cbk ──────  
  打印 "ACK received from client!"
```
