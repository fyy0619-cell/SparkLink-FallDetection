# 信号量 + 消息队列 —— 稳定采样流水线（从"两条执行流"讲起）

> 承接 [硬件定时器(Timer)驱动](硬件定时器(Timer)驱动.md)。本文讲清 200Hz 采样任务里比"最小定时器 demo"多出来的三样东西：
> **两条并行执行流、信号量(报时)、消息队列(传数据)**。理解了就能自己写这种"稳定采样流水线"。
> 对应源码：`main_task.c` 的 `sample_timer_cb` + `Sample_Task_Body`。

---

## 🔑 核心要点（先记住这三条，全篇都在解释它们）

> **① 这段代码有两条【并行的执行流】，不是一条线顺着走的。**
> **② `uapi_timer_start` 只"上闹钟"就立即返回，它【不调用】回调；回调是 5ms 后由硬件中断在【另一条流】里触发的。**
> **③ 信号量传"时机/节拍"，消息队列传"数据"——两者解决不同问题。**

---

## 一、最容易栽的坑：你以为是一条线，其实是两条

看这段：
```c
static void Sample_Task_Body(void *arg) {
    while (1) {
        osSemaphoreAcquire(g_tick_sem, osWaitForever);                 // 等信号
        uapi_timer_start(g_sample_timer, SAMPLE_PERIOD_US, sample_timer_cb, 0); // 重载
        MPU6050_Read_Accel_Gyro(...);                                  // 读IMU
        osMessageQueuePut(g_imu_queue, &sample, 0U, 0U);               // 入队
    }
}
static void sample_timer_cb(uintptr_t d) {   // 回调
    osSemaphoreRelease(g_tick_sem);
}
```

**常见疑问：执行完 `uapi_timer_start` 下一步跳哪？是读 IMU 还是 `osSemaphoreRelease`？**

> ⭐ **答案：跳到下一行——读 IMU。不是 `osSemaphoreRelease`。**
> 因为 `uapi_timer_start` **只是"上好一个 5ms 的闹钟"然后立即返回，它不会调用回调**。
> 回调 `sample_timer_cb`（里面的 `osSemaphoreRelease`）是 **5ms 之后由硬件中断触发的，在另一条独立执行流里**。

## 二、两条执行流（带时间轴）

```
【任务流】Sample_Task_Body —— 顺着一行行走：
  acquire(睡等) →[被唤醒]→ start(上5ms闹钟,立即返回) → 读IMU → 入队 → 回到while顶 → acquire(又睡等) ...

【中断流】sample_timer_cb —— 每5ms被硬件"插进来"一次，独立发生：
  [5ms到] 硬件中断 → 驱动ISR → sample_timer_cb → osSemaphoreRelease(发信号)
```

在时间轴上它俩是这样交替的：

```
时间 →   0ms        5ms        10ms       15ms
任务流:  采样...睡  [醒]采样..睡 [醒]采样..睡 [醒]...
中断流:      ↑release    ↑release    ↑release      ← 每5ms一次，把任务叫醒
```

> 🔑 **`uapi_timer_start` 属于任务流，做的是"预约 5ms 后让中断流跑一次"，然后任务流自己继续往下（去读 IMU）。**
> **`osSemaphoreRelease` 属于中断流，时候到了才被硬件触发——不是 `uapi_timer_start` 调它的。**
> 这也呼应"回调不是你顺着调的，是硬件到点插进来调的"。

---

## 三、信号量（semaphore）：两条流靠它"握手"

信号量 = 一个**会计数的"令牌/许可"**，配两个动作：

| 动作 | 含义 |
|---|---|
| `osSemaphoreAcquire`（拿令牌） | 有令牌就拿走继续跑；**没令牌就睡等**（`osWaitForever`=一直睡到有为止） |
| `osSemaphoreRelease`（放令牌） | 放一个令牌进去，**唤醒正在睡等的那个人** |

在流水线里：
```
中断流(每5ms): osSemaphoreRelease → 放令牌 → 唤醒任务
任务流:        osSemaphoreAcquire → 没令牌就睡；被唤醒后拿走 → 继续采样
```

> ⭐ **整个节奏 = 任务平时睡在 `acquire` 上，中断每 5ms `release` 一次把它叫醒，它醒来采一次样，又回去睡。信号量就是"中断 → 任务"的报时铃。**

**为什么不用任务自己 `osDelay(5ms)`？**
因为 `osDelay` 受调度影响会**抖**；硬件中断报时**精准**。信号量把"精准的硬件节拍"传给任务。

---

## 四、消息队列（message queue）：带缓冲的传送带

队列 = 一条**先进先出的传送带**，配两个动作：

| 动作 | 含义 |
|---|---|
| `osMessageQueuePut`（放） | 把一份数据放上传送带（采样任务用） |
| `osMessageQueueGet`（取） | 从传送带取一份（推理任务用） |

```
采样任务: 读到一帧IMU → Put 进队列
推理任务: 从队列 Get 出来 → 跑 TinyML
```

**为什么要队列而不是直接传？** 两边速度不一样：采样稳定 200Hz，推理可能慢。队列当**缓冲区**，采样只管按节拍放，推理慢慢取。

> ⭐ **放的时候用 `Put(..., 0U, 0U)`（不等待）：队列满就立即返回失败 → `g_drop_count++` 丢帧计数。**
> **保证采样节拍不被拖住——"保节拍 > 保每一帧"，这是实时系统的优雅降级。**

---

## 五、信号量 vs 消息队列：分工（关键区别）

| | 信号量 | 消息队列 |
|---|---|---|
| 传的是 | **时机/节拍**（"该干活了"） | **数据**（采到的样本） |
| 带不带数据 | 不带 | 带 |
| 解决什么 | **何时**做 | **传什么** |
| 满/空处理 | 计数增减 | 满则丢（本项目） |

整条流水线：
```
中断(5ms) ──信号量(报时)──▶ 采样任务 ──消息队列(传数据)──▶ 推理任务
           "节拍到了"          读IMU           "一帧数据"        跑AI
   精准硬件节拍            中优先级              缓冲             低优先级慢慢消费
```

## 六、和"最小定时器 demo"的对照

| | `timer_hello`（简化版） | `Sample_Task_Body`（生产版） |
|---|---|---|
| 回调干啥 | `tick++` | `osSemaphoreRelease`（发信号） |
| 任务干啥 | 打印 | 重载 + 读IMU + 入队 |
| 节拍怎么传 | 全局变量 tick | **信号量** |
| 多了什么 | — | **信号量 + 消息队列 + 满则丢降级** |

> 骨架完全一样（回调发信号、任务干重活），生产版只是把"传节拍"升级成信号量、再加一条队列缓冲。**你已经亲手搭过 demo，这个就看得懂了。**

---

## 七、一句话总结

> `uapi_timer_start` 执行完**顺着往下去读 IMU**；`osSemaphoreRelease` 是 **5ms 后硬件中断在另一条流里**触发的，不是它调的。
> **信号量**是中断给任务的"报时铃"（release 唤醒 acquire），传节拍；**消息队列**是采样任务给推理任务的"传送带"（put/get + 满则丢），传数据。
> 两条执行流靠信号量握手、靠队列传货，合起来就是**稳定的采样流水线**。
