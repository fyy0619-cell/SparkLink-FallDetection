# WS2812B 灯光报警驱动

> 跌倒检测系统的本地声光报警中"光"的部分：用一条 WS2812B RGB 灯带，待机显示绿色，
> 收到跌倒事件后切换为红色闪烁，提示现场和周围人员。
>
> 本文记录灯带的接线、报警灯示设计，以及一次**数据时序失真故障**（颜色错乱 / 灯珠不亮）
> 的完整排查与修复过程。
>
> 对应固件文件（在独立的 WS63 SDK 工程中维护）：
> `application/samples/my_demo/fall_detect/src/ws2812b.c`、`inc/ws2812b.h`

---

## 1. 功能概述

| 状态 | 灯示 | 触发条件 |
|------|------|----------|
| 待机 | 8 颗灯珠常亮**绿色** | 上电 / 复位后默认 |
| 报警 | 8 颗灯珠**红色闪烁**（2.5 Hz） | `sle_client_task.c` 收到 `0x05` 跌倒事件，置位 `g_ws2812b_alert_active` |

报警与待机由一个独立任务 `ws2812b_flash_task` 驱动，通过全局标志 `g_ws2812b_alert_active`
在两种状态间切换。

---

## 2. 硬件接线

| 项目 | 取值 | 说明 |
|------|------|------|
| 数据脚 | `GPIO_10` | 避开 `GPIO_07/08`（UART2）冲突 |
| 灯珠数量 | 8 | `WS2812B_NUM_LEDS` |
| 灯带供电 | 5 V | WS2812B 标称 VDD 3.5 ~ 5.3 V |
| 驱动能力 | `PIN_DS_7` | 拉满驱动强度，改善单总线信号沿 |

> **电平注意**：WS63 GPIO 输出为 3.3 V，而灯带按 5 V 供电时，逻辑高判决门限约为
> `0.7 × 5 V ≈ 3.5 V`，3.3 V 信号处于门限边缘。本工程实测可用（首颗灯能正确解码后，
> 会以 5 V 电平重整信号再向后传递），但若后续出现首颗灯不稳定，应优先考虑加电平转换，
> 或把灯带供电降到 ~4 V 让 3.3 V 信号可靠过门限。

## 3. 报警灯示设计

### 3.1 状态机

报警/待机由 `ws2812b_flash_entry()` 任务实现：

- `g_ws2812b_alert_active == true`：红色闪烁，每 `WS2812B_ALERT_HALF_PERIOD_MS` 翻转一次（红 ↔ 灭）。
- `g_ws2812b_alert_active == false`：维持待机绿色，仅在状态切换边沿重绘一次，避免高频刷屏。
- 状态切换时强制重绘，避免红 ↔ 绿过渡残留中间帧。

### 3.2 闪烁频率：为什么是 2.5 Hz

最初实现为 **5 Hz**（100 ms 红 / 100 ms 灭）。后调整为 **2.5 Hz**（200 ms 红 / 200 ms 灭）：

- 人眼对 **2 ~ 3 Hz** 的高对比闪烁最敏感，这个节奏也最符合"警报"的直觉。
- 5 Hz 偏快，红光全亮快闪看着发"毛"，不够像报警，长时间观看易疲劳。
- 慢一拍反而更醒目、更像告警。

调整方法很简单，只改 `ws2812b.h` 一个宏：

```c
/* 报警闪烁周期：2.5 Hz = 200ms 红 / 200ms 灭 */
#define WS2812B_ALERT_HALF_PERIOD_MS  200
```

## 4. 单总线时序协议简介

WS2812B 没有时钟线，靠**单根数据线上高电平的"长短"**区分 0 码和 1 码：

- `0` 码：一段**短**高电平 + 一段长低电平
- `1` 码：一段**长**高电平 + 一段短低电平
- 每颗灯吃掉数据流最前面的 24 bit（颜色顺序 **G R B**，高位先发），把剩余 bit
  整形后转发给下一颗，从而实现"一根线串起一整条灯带"。
- 一帧发完后拉低 ≥ 50 µs 作为复位（latch），灯珠才把收到的颜色锁存显示。

> **关键点**：因为是靠"高电平时长"编码，**位时序必须准**。高电平偏短，`1` 码会被
> 误读成 `0`；时序整体发飘，信号会沿灯带逐颗劣化。这正是下面这次故障的根源。

各段目标时长（兼容 WS2812B / WS2812B-V5 / SK6812 的折中值）：

| 段 | 含义 | 目标时长 |
|------|------|----------|
| `T0H` | 0 码高电平 | 350 ns |
| `T1H` | 1 码高电平 | 700 ns |
| `T0L` | 0 码低电平 | 800 ns |
| `T1L` | 1 码低电平 | 600 ns |

## 5. 故障现象

报警时灯带表现异常（实测视频复盘）：

1. **颜色不是纯红**，更像任意颜色在乱跳。
2. **只有前 2 颗灯珠在闪烁**，第 3、4 颗亮着但不闪。
3. **一共只有 4 颗灯珠亮**，后面 4 颗完全不亮。

"前面的灯还能动、越往后越乱、最后干脆不亮" —— 这是 WS2812B **数据信号沿灯带逐级失真**
的典型特征：不是报警逻辑的问题，是底层 bit 时序出了问题。

---

## 6. 根因分析

旧实现用一个 `nop` 计数循环模拟延时：

```c
static inline void ws2812b_delay_cnt(uint32_t cnt)
{
    while (cnt-- > 0) {
        __asm__ volatile ("nop");
    }
}
```

并用经验值 `T1H_CNT / T0H_CNT / ...` 控制各段时长。问题出在**编译优化档位不一致**：

- 代码注释里写明，这些 `CNT` 经验值是按 **`-O0`** 调出来的（`-O0` 下每圈循环约 10~12 个周期）。
- 但实际发送函数 `ws2812b_send_byte()` 标了 `__attribute__((optimize("O2")))`。
- `-O2` 下，延时循环的计数自增、比较、跳转被大幅收紧，每圈只剩约 3~4 个周期。

结果：**同样的 `CNT` 值，在 O2 下产生的延时只有 O0 预期的 1/2 ~ 1/3**。
每个高/低电平脉宽都远低于 WS2812B 规格（`T1H` 应 ≈ 0.8 µs，实际可能只有 ≈ 0.35 µs）。

为什么是"前面能动、后面失效"：

- 第 1、2 颗灯对边缘时序还有一点容差，能勉强解码（所以前两颗会闪，但颜色已经开始偏）。
- 每颗灯把数据整形后转发，时序本就处在临界点，误差沿灯带逐级累积。
- 到第 3、4 颗，收到的已是错乱数据，锁存后不再随帧更新（亮但不闪）。
- 到第 5 ~ 8 颗，信号彻底无法识别 —— 直接不亮。

**一句话**：延时参数与编译优化档位脱节，导致位时序整体偏短、灯带后段数据失真。

---

## 7. 解决方案：周期计数器 + 主频自标定

修复思路：**让延时不再依赖"猜 nop 圈数"，改用硬件周期计数器精确计时**。

### 7.1 用 RISC-V `cycle` CSR 计时

WS63 的 RISC-V 核带有 `cycle` 周期计数器 CSR，每个 CPU 时钟自增 1。
直接读它做忙等，时长与编译优化档位**完全无关**：

```c
static inline __attribute__((always_inline)) uint32_t ws2812b_rdcycle(void)
{
    uint32_t c;
    __asm__ volatile ("csrr %0, cycle" : "=r"(c));
    return c;
}

/* 忙等 cyc 个 CPU 周期；32 位无符号相减天然处理计数器回绕。 */
static inline __attribute__((always_inline)) void ws2812b_wait_cyc(uint32_t cyc)
{
    uint32_t start = ws2812b_rdcycle();
    while ((ws2812b_rdcycle() - start) < cyc) {
        /* busy wait */
    }
}
```

### 7.2 用 TCXO 自动标定 CPU 主频

要把"纳秒时长"换算成"周期数"，需要知道 CPU 主频。但本工程里 **WS63 核心频率不是一个
写死的编译期常量**（`clock_init.c` 只设置了 UART / 系统时钟，核心频率并未固定值）。
硬编频率（如 160 MHz）一旦与实际不符，时序就会整体成比例跑偏。

因此改为**上电时自动标定**：用独立的 TCXO 微秒计数器测量一段已知时间窗内 CPU 走过多少周期，
得到 `cycles/µs`（即核心频率），再把纳秒目标值换算成周期数。

```c
static void ws2812b_timing_calibrate(void)
{
    uint64_t us0 = uapi_tcxo_get_us();
    while (uapi_tcxo_get_us() == us0) { /* 对齐到微秒计数跳变沿 */ }
    us0 = uapi_tcxo_get_us();
    uint32_t cyc0 = ws2812b_rdcycle();
    while ((uint32_t)(uapi_tcxo_get_us() - us0) < 5000U) { /* 测量 5 ms */ }
    uint32_t elapsed_cyc = ws2812b_rdcycle() - cyc0;
    uint32_t elapsed_us  = (uint32_t)(uapi_tcxo_get_us() - us0);

    if (elapsed_us < 1000U || elapsed_cyc == 0U) {
        /* TCXO 读数异常 -> 保留兜底周期数 */
        return;
    }
    uint32_t cyc_per_us = (elapsed_cyc + elapsed_us / 2U) / elapsed_us;
    g_cyc_t0h = cyc_per_us * WS2812B_T0H_NS / 1000U;
    g_cyc_t1h = cyc_per_us * WS2812B_T1H_NS / 1000U;
    g_cyc_t0l = cyc_per_us * WS2812B_T0L_NS / 1000U;
    g_cyc_t1l = cyc_per_us * WS2812B_T1L_NS / 1000U;
}
```

要点：

- `cycle` 计数器与 TCXO 微秒计数同为"墙上时钟"。标定期间即使任务被抢占，两者一起前进，
  比值仍等于核心频率 —— 所以**标定无需关中断**。
- 标定在 `ws2812b_init()` 里、发送任何灯带数据**之前**执行一次。
- TCXO 读数异常时保留兜底周期数（约对应 160 MHz），不至于完全失效。

### 7.3 位发送改用周期延时

```c
__attribute__((optimize("O2")))
static void ws2812b_send_byte(uint8_t byte)
{
    for (int bit = 7; bit >= 0; bit--) {
        if (byte & (1u << bit)) {
            ws2812b_pin_high_fast();
            ws2812b_wait_cyc(g_cyc_t1h);
            ws2812b_pin_low_fast();
            ws2812b_wait_cyc(g_cyc_t1l);
        } else {
            ws2812b_pin_high_fast();
            ws2812b_wait_cyc(g_cyc_t0h);
            ws2812b_pin_low_fast();
            ws2812b_wait_cyc(g_cyc_t0l);
        }
    }
}
```

`O2` 此处只为收紧位循环开销，**时序本身已不再依赖优化档位**。
一帧数据仍在 `osal_irq_lock()` / `osal_irq_restore()` 之间发送，避免中断打断单颗灯的时序。

## 8. 时序配置（`ws2812b.h`）

旧的 `T1H_CNT` 等 `nop` 圈数宏已删除，替换为**纳秒**定义，直观且与平台无关：

```c
/* 位时序（纳秒）—— 高/低电平时长用 RISC-V cycle 计数器精确计时 */
#define WS2812B_T0H_NS   350   /* 0 码高电平 */
#define WS2812B_T1H_NS   700   /* 1 码高电平 */
#define WS2812B_T0L_NS   800   /* 0 码低电平 */
#define WS2812B_T1L_NS   600   /* 1 码低电平 */
```

这 4 个值是兼容 WS2812B / WS2812B-V5 / SK6812 的折中值，正常无需改动。

## 9. 验证方法

烧录后，开机串口会打印一行标定日志：

```text
[WS2812B] calibrate: <N> cyc / <M> us = <F> cyc/us; T0H=.. T1H=.. T0L=.. T1L=.. (cycles)
```

- `<F> cyc/us` 即 CPU 主频（MHz），应为一个合理整数（如 ~160 / ~240）。
- 若打印 `calibrate failed`，说明 TCXO 取数异常，需进一步排查。

**实测结果**：复位后 8 颗灯珠全部显示绿色；触发跌倒报警后，8 颗灯珠全部转为红色并同步
闪烁，颜色纯正、无错乱、无掉灯。故障修复完成。

---

## 10. 经验总结

1. **`nop` 计数延时与编译优化强耦合**。一旦优化档位变化（或注释/代码不同步），所有
   时序经验值集体失真。位带（bit-bang）这类时序敏感代码，应优先用**硬件计数器**
   （周期计数器 / 定时器）计时，而非 `nop` 圈数。
2. **不要硬编 CPU 主频**。当主频不是编译期固定常量时，用一个独立可信时基（本例的 TCXO）
   在运行时自标定，时序参数才能跨频率、跨板子稳定。
3. **WS2812B 故障特征要会读**：颜色错乱 + 后段灯珠不亮 = 数据信号沿灯带逐级失真，
   九成是位时序问题（或供电 / 电平问题），而非业务逻辑问题。
4. **时序参数用物理单位表达**。把 `T0H_CNT=7` 这种"魔法圈数"换成 `WS2812B_T0H_NS=350`，
   可读性和可移植性都更好。
5. **报警灯示别贪快**。2 ~ 3 Hz 的慢闪比 5 Hz 快闪更像"警报"，也更醒目。
